# VHS-15 — Optional scaling-advocate reviewer for /spec-cycle (the "case of N" lens)

**Status:** Backlog (exploratory) · **Priority:** Low · **Assignee:** Devin
**Created:** 2026-06-14 · **Plane:** VHS-15 — "Add a scalability / 'power-user advocate' lens to /spec-cycle review loop" *(verified 2026-06-16; ticket is exploratory, not yet specced, A-vs-B undecided — see "Verification status")*
**Origin:** Filed 2026-06-14 (raised 2026-06-15 in the body) as an exploratory note — *"scalability could be a blind-spot in the /spec-cycle review loop"* — wanting a constant frame for the review council: *"what if the user had need for N instances of this code?"* The forcing function making it live now is the **Serenade hackathon** (Nvidia / Nous Research / Stripe stacks): a Hermes agent standing up to autonomously run the business is, by definition, a "case of N" — continuous autonomous operation, throughput, multi-tenant fan-out, cost-at-scale. The gap is that **scaling has no advocate** in the lifecycle; it surfaces in PR review, if at all, by which point the direction is already baked in. Unless scale is named in the brief, nobody argues for it. *(The Serenade/hackathon framing is this cycle's added context; the ticket itself cites only the general blind-spot — see "Verification status".)*

## Goal

Give `/spec-cycle` an **optional fourth review lens** — a scaling advocate, the power-user for the case of N — that the spec author toggles **on per-brief** when scale is a real factor. When off (the default), spec-cycle behaves exactly as it does today: the three-lens loop, unchanged. When on, the scaling lens dispatches alongside the existing three, reads the same spec, and folds its findings into the same severity gate. The point is to move the scaling argument **upstream into the brief/spec**, where direction is still negotiable, instead of discovering it at PR review when it is too late.

## Context (verified 2026-06-16 against the repo)

- **There are exactly three reviewer lenses today, and none of them owns scale.** `agents/` contains `spec-reviewer-correctness.md`, `spec-reviewer-edge-cases.md`, and `spec-reviewer-conventions.md` — nothing else. `spec-cycle` step **2b** (`skills/spec-cycle/SKILL.md:268–275`) dispatches them as a **hardcoded** trio of parallel `Agent` calls (`spec-reviewer-correctness` / `spec-reviewer-edge-cases` / `spec-reviewer-conventions`). The count "3" is wired into the dispatch, the save paths (step 2c, `round-<N>/{correctness,edge-cases,conventions}.md`), and the prose ("3-lens parallel review") across `SKILL.md`, `AGENTS.md`, and `docs/spec-workflow-reference.md`.
- **The closest existing lens is edge-cases, and it deliberately stops short of scale.** `spec-reviewer-edge-cases` probes *correctness under stress* — empty/null inputs, races, external-down, **size limits as a crash/corruption axis**, persistence atomicity/idempotency/size-bounds (`agents/spec-reviewer-edge-cases.md`). But it scores by *"does it break"*, not *"does it hold at the target N"*: per its own rubric, an unhandled edge that **degrades gracefully** is P2-or-below. A design that works correctly at N=1 and is architecturally unable to reach N=10⁶ — wrong data structure, unbounded per-request work, no batching/pagination, synchronous fan-out, per-item LLM calls in a hot loop — passes the edge-cases lens. That is precisely the blind spot.
- **The gate is a sum across whatever reviewers ran.** Step 2c computes `total_p0p1` across the dispatched reviewers and breaks the loop at zero (`SKILL.md` step 2c/2d). A fourth lens folds into that arithmetic for free — *if* it emits the same `STATUS:` contract.
- **The severity scale is shared and load-bearing.** P0 = internally inconsistent / nonexistent refs / contradicts a "Done when". P1 = non-functional code or violates a load-bearing brief decision. **P2+ is advisory and never blocks.** Any new lens must reuse this scale verbatim (`AGENTS.md` "Conventions"; each `agents/spec-reviewer-*.md` "Severity definitions").
- **The brief is the right place for the toggle.** Phase 3's drift-check reads *"Decisions carried in brief"* and *"Out-of-scope fences"* back against the spec (`SKILL.md` Phase 3; `docs/spec-workflow-reference.md` Phase 3). A scale declaration carried in the brief is therefore already in the contract the lifecycle checks against — the author decides, the brief records it, spec-cycle reads it.
- **Capability declaration has a worked precedent.** `spec-cycle` is the one skill carrying a `requires:` block; the repo's "declare-don't-infer" discipline (VHS-18/VHS-20) is the model — the scaling lens runs because the brief *declares* scale relevant, never because spec-cycle *guesses* it from the spec body.
- **The ticket is exploratory and leaves two things open; this brief closes them.** VHS-15 (verified 2026-06-16) is filed as *"exploratory — to look into the angle. Not yet specced; no implementation decision (A vs. B) made."* It frames two options — **(A)** fold a scale dimension into the edge-cases reviewer, or **(B)** add a fourth `spec-reviewer-scalability` agent — and leans toward an **always-on / "constant frame"** advocate. It also enumerates the differentiator vs. edge-cases (*edge-cases = "correct under one adverse input?"*; *scalability = "does the design hold at N×?"*) and concrete smells to hunt: per-item work that should be batched, O(N) where O(1) exists, unbounded accumulation, per-instance state that collides across instances, fan-out without a concurrency cap, a singular config/path/identifier where a power user wants many. This brief adopts that differentiator and smell-list verbatim, **resolves A-vs-B → B**, and **departs from the ticket's "constant" lean in favor of opt-in** (see Decisions carried forward — both are deliberate, recorded calls made with the requester this cycle).

## Decisions carried forward

- **Opt-in, author-owned, off by default — a deliberate departure from the ticket's "constant frame" lean.** VHS-15's body leans toward an always-on advocate; this brief instead makes scale a factor the **spec author** names in the brief, because most fixes are genuinely small and an always-on fourth lens taxes every pass (cost, convergence, false-positive scale findings on N=1 work) for no return. Absent an explicit scale declaration, the lens does not run and spec-cycle is byte-for-byte unchanged. There is no auto-detection or inference — silently inferring scale relevance would violate declare-don't-infer and re-introduce the "decided too late" failure from the other direction. *(This resolves the ticket's open "constant vs. triggered" question against its stated lean; if the council wants always-on instead, only the toggle's default flips — the rest of this brief stands.)*
- **Implementation = option B (a new fourth agent), not option A (fold into edge-cases).** This resolves the ticket's explicit open A-vs-B decision, using the ticket's own stated risk for A: folding a scale dimension into `spec-reviewer-edge-cases` "risks diluting that reviewer's focus and burying scale findings under edge-case noise." A standing, separately-scored lens keeps the case-of-N argument crisp and independently gated. The edge-cases-vs-scalability differentiator and smell-list from the ticket are written into the new agent's prompt so the lens never degenerates into re-finding edge cases.
- **One declaration, in the brief, with a target N.** The toggle is a brief field that names the scaling dimension(s) and the **target scale the design must hold at** (e.g., requests/sec, records, tenants, concurrent agents, $/op). "Scaling matters" without a target is not actionable; a target is what lets the lens score P0/P1 vs. advisory. The spec author may also explicitly mark scale a **non-factor**, which is recorded and respected.
- **The lens is a peer reviewer, not a new stage — it does not touch the pass budget.** It is a fourth `agents/spec-reviewer-scalability.md` dispatched in the **same** parallel 2b message, saved to `round-<N>/scalability.md`, emitting the **same** `STATUS: GREEN | RED P0=… P1=…` contract, read-only, never editing files or git state — identical to the existing three (`AGENTS.md` "Conventions"; reviewer output contract). Because it runs *within* a round rather than adding one, the up-to-4-pass cap and the session-boundary HARD STOP are unchanged — this directly answers the ticket's "does a 4th reviewer push past the pass budget?" open question: no.
- **Same severity scale; the opt-in toggle *is* the severity-calibration answer.** The ticket worries that "a scale concern that's real but only bites at 100× should not block a spec the way a correctness bug does." The opt-in + declared-target-N model resolves exactly this: blocking severities apply **only** when the author has declared that N load-bearing. When on, a design that **cannot reach the declared target N** is P1 (the scaling analogue of "non-functional code") and a self-contradiction against a declared scale "Done when" is P0; everything that merely "bites beyond the declared N" or "would be nicer at scale" stays P2+ advisory. The lens reuses the shared rubric verbatim — no parallel severity ladder.
- **Scope is architectural *and* operational scale.** Answering the ticket's third open question: because VHS specs are largely skill-shaped, the lens covers both structural scaling (data structures, algorithmic complexity, fan-out/concurrency, batching, per-instance state collision) **and** operational scale (cost-per-op, latency, and token/context budget under repeated/large-N invocation). The declared target N may be expressed in any of these units.
- **Security-first (pairs with the Petasos posture).** Scale is also a security surface: the lens explicitly covers resource-exhaustion / DoS, missing rate-limits and backpressure, unbounded fan-out as an amplification vector, and cost-blowout as a denial vector. A scale-driven security regression is rated on the shared scale, not softened because it only bites "at N". The reviewer is parse-and-read-only — no execution of spec or skill content.
- **No regression of the lifecycle invariants.** The session boundary, the three load-bearing existing lenses, read-only reviewers, the `STATUS`-line gate protocol, round-2+ closure tracking, and the Phase 3 drift-check HARD STOP are all untouched. The fourth lens is additive and gated; it cannot weaken the existing gate.

## Done when

- A new `agents/spec-reviewer-scalability.md` exists, following the established reviewer shape (grounding step → critique lens → shared severity definitions → output contract with a machine-parseable `STATUS:` last line), read-only, with the edge-cases-vs-scalability differentiator and the ticket's smell-list written into its critique lens.
- `spec-cycle` step 2b **conditionally** dispatches the scalability reviewer in the same parallel message as the existing three **iff** the brief declares scale a factor; its report is saved to `docs/specs/TODO/<TICKET-ID>.reviews/round-<N>/scalability.md`, and its P0/P1 fold into the step-2c `total_p0p1` gate and the round-2+ closure tracking exactly as the other lenses do.
- When the brief carries **no** scale declaration (or marks scale a non-factor), spec-cycle's behavior is **unchanged** — three lenses, no `scalability.md`, identical gate arithmetic — and a test/checklist demonstrates that no-op.
- The brief schema (and `docs/spec-workflow-reference.md`) documents the scale-declaration field: how to turn the lens on, how to state the target N, and how to mark scale an explicit non-factor.
- The Phase 3 drift-check accounts for a declared scale target as a carried-forward decision (it is checked back against the spec like any other brief decision).
- Docs/prose that hardcode "3-lens" are reconciled to describe the default-three / optional-fourth shape (`AGENTS.md`, `SKILL.md` description, `docs/spec-workflow-reference.md`).

## Out of scope

- **Making the lens run by default or auto-detecting scale.** It is opt-in per brief, full stop. Auto-inference is explicitly rejected.
- **A fifth/Nth pluggable-reviewer framework.** This adds exactly one optional lens with a brief-level toggle; a general reviewer-registry/plugin system is a premature abstraction at N=1 and is not authorized here.
- **Re-scoring or re-tuning the existing three lenses**, or changing the shared severity rubric, the gate formula, or the round cap.
- **Performance/load testing, benchmarking, or profiling of any target system.** The lens argues about scale at the *spec* level (data structures, algorithmic complexity, fan-out shape, batching, backpressure); it does not run load tests or measure anything.
- **Implementing Serenade, the Hermes autonomous-business agent, or any hackathon deliverable.** Serenade is the forcing function that motivates this lens, not work delivered by this ticket.
- **Touching `/ship-spec`, `/spec-close`, or `/review-pr`** — this change is contained to `/spec-cycle` and its agents.
