### F-1: Folding an in-scope P0 the reviewer filed under the D14 exception does not discharge the row, so the ceiling violation is guaranteed to fire the next round
**Severity:** P1
**Where:** spec § Design 1 step 3/4 (spec.md:93-94) vs § Design 2 R2(c) (spec.md:126) and § Design 7 block (spec.md:181)
**Edge case:** A row records an in-scope P0 (mis-routed, or re-classified by the conventions lens under D17). The reviewer takes the exception the block now grants: "*file it once, as a P0 titled `routing violation: D-<n>` … unless you are filing the underlying P0 under the exception below*". So in that round **no routing violation is filed** — only the underlying P0.
**What happens:** The author routes the underlying P0 through Design 1: in-scope, 2+ sites → step 3 says "**fold**: edit every site on the list", step 4 says disposition it `fixed: edited § <a>; § <b>`. Neither step mentions the row. R2(c)'s two triggers are (i) "a row the reviewers filed a ceiling-class `routing violation: D-<n>` against" and (ii) "whose `Scope` repair under (a) turns it into an in-scope P0 row" — neither fires here, because the reviewer deliberately filed the underlying P0 *instead of* the violation. So the defect is fixed and the row still reads P0 / in-scope with no `Discharged:` field.

Next round the underlying P0 no longer exists, so the exception no longer applies and every lens files `routing violation: D-<n>` — up to four P0s for a defect that was already fixed. Cost:
- rounds 1→2 or 2→3: one wholly wasted RED round, then R2(c) resolves it (the author appends `Discharged:` over an already-done fold, which R2(c) does not contemplate either — it says "fold … **in the same round** and append").
- round 3→4: the violation lands in round 4. 2e's round-4 branch runs the rewrite, then 2f halts red unconditionally — there is no round 5 to observe the discharge. The run burns on a P0 whose underlying defect was fixed in round 3. That is the failure mode the closure of round-1 F-1 was meant to eliminate, reached through the one door the fix did not cover.
**Why the spec misses it:** R2(c) was written from the reviewer's side (a violation *was filed*, now discharge it). The D14 exception, added in the same round to answer correctness/R1/F-6, creates a path where the state exists but no violation is filed — so the author is never handed the trigger. Nothing in Design 1's fold branch knows rows exist. Secondary readability hazard: "discharge" already means something else at spec.md:96 (a Settled grill decision is "discharged" by *appending* a row), so the two senses collide in one section.
**Suggested fix:** Wire the fold branch to R2(c). In Design 1 step 4's Fold branch: "If the finding cites a row `D-<n>` (the D14 in-scope-P0 exception), discharge that row under R2(c) in the same round: append `**Discharged:** folded round <n> — § <a>; § <b>` naming the sections this fold touched." And add the third trigger to R2(c): "…, or a row whose finding you fold under Design 1 step 3's in-scope-P0 branch — in that case the fold *is* the discharge and no prior violation is required." Add to the Design 7 block one sentence so the lens can verify it: "A row you cite when filing an in-scope P0 under the exception must carry `Discharged:` by the next round; if the P0 was folded and the row still carries none, that is the `routing violation: D-<n>` this block files." Consider renaming the spec.md:96 grill sense to avoid the collision.

### F-2: The new fence rule never says what *opens* a fence — a `> `-quoted or inline fence marker flips parity and makes the whole section silently invisible
**Severity:** P1
**Where:** spec § Design 2 (spec.md:104), § Design 7 block (spec.md:181), inherited by § Design 5 (spec.md:166)
**Edge case:** The clause reads: "A line prefixed `> `, **or inside a fenced code block (between matching triple-backtick or triple-tilde fences, counted from the top of the file)**, is never a heading, never a section terminator, and never a row." It states what a quoted line *is not*; it never states that a quoted line does not **open or close** a fence, and it does not require the marker to begin the line. Three routine triggers:
1. **A `Suggested fix` containing a fenced block.** The row shape stores the reviewer's text verbatim, every line prefixed `> ` (spec.md:115) — so a fix that quotes a ```` ```text ```` block becomes `> ```text` … `> ``` `. Under "counted from the top of the file" with no blockquote exclusion, those open and close a fence. A balanced pair is survivable; an **unbalanced** one is not — and unbalanced is easy: a fix that shows only an opening fence, a fix quoting a ```` ```markdown ```` example that itself contains a fence (three markers), or a fix truncated mid-block.
2. **Inline triple backticks.** Nothing says the marker must be at line start. Round-1 edge-cases/F-3's own Suggested fix contains the text "between matching ``` or ~~~ fences" inside inline code spans — exactly the kind of text that gets stored verbatim in a row.
3. **Any earlier unbalanced fence in the spec**, since parity is global from the top of the file.
**What happens:** Parity flips and everything below is "inside a fenced code block", i.e. never a heading, never a row, never a terminator. Consequences, all silent:
- Design 5 renders `(none)` (or drops every row below the flip) — and Design 6's tripwire *mis-attributes* it: "A spec that carried rows in a prior round and renders `(none)` now is the signature of a truncated write" (spec.md:173) sends the operator to `git diff` for a write that never happened.
- Every reviewer's Deferred-findings block finds no section, so D14 suppression never fires and **every deferred finding is re-filed** — the exact oscillation loop the ticket exists to break, now caused by the mechanism meant to stop it.
- If the flip lands mid-section, the surviving rows are checked and the rest are not, so a malformed row can pass unnoticed.
There is no loud failure anywhere on this path.
**Why the spec misses it:** The fence exclusion was added to answer round-1 F-3, whose trigger was a heading inside a fence in the spec's *prose*. Nobody re-ran the rule against the one place the spec deliberately stores arbitrary reviewer text — the `> `-prefixed `Suggested fix`, which the spec itself calls out (spec.md:77) as "the one place a reviewer's text is transformed on the way into the spec".
**Suggested fix:** Extend the byte-identical clause in both places (Design 2 spec.md:104 and the Design 7 block spec.md:181) with the two missing predicates, e.g.: "A fence marker counts only when three or more backticks or tildes **begin the line** (up to three leading spaces) **and the line is not prefixed `> `** — a fence marker inside a blockquote neither opens nor closes a fence, so a `Suggested fix` may quote fenced text safely." Add to the Design 6 bullet: "an unbalanced fence earlier in the spec has the same `(none)` signature as a truncated write; check fence parity before concluding truncation." Test-plan row 6/8: add `grep -cF 'begin the line'` ≥ 1 per agent and in SKILL.md.

### F-3: A discharged row's render hides the operator's backfilled ticket id, falsifying the Done-when mapping
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec § Design 5 (spec.md:166) vs § Done when (spec.md:215)
**Edge case:** A row is filed as a ticket (`Follow-up: VHS-99`, D12's operator hand-edit) and is later discharged under R2(c).
**What happens:** Design 5: "`Follow-up:` is printed verbatim, **except that a row carrying `Discharged:` prints that field's value in the Follow-up column**." The render is the operator's only surface on the section, so a discharged row with a filed ticket shows `folded round 3 — § …` and never shows `VHS-99` — the operator has an open ticket for a defect that is now fixed and no on-screen pointer to close it. This directly falsifies the spec's own Done-when mapping at spec.md:215: "Design 5 renders the field's value **verbatim**." Two sentences in the spec disagree about the same column. (Filed P2 rather than P0 because the row still carries the id — the criterion "deferred entries that become tickets carry the ticket id" holds on disk; only the render and the mapping sentence disagree.)
**Why the spec misses it:** The `Discharged:` column reuse was the cheapest way to surface the new field without adding a column; the interaction with a *backfilled* `Follow-up:` value — the only value the Done-when cares about — was not scored.
**Suggested fix:** Print both, and correct the mapping: in Design 5, "a row carrying `Discharged:` appends ` [discharged: <value>]` after the `Follow-up:` value, which is still printed verbatim"; leave spec.md:215 as it stands. One site each.

### F-4: A same-root finding on a *discharged* row is routed into that row, producing a row that is simultaneously discharged and newly deferred
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec § Design 1 step 4 (spec.md:94), § Design 2 R2 (spec.md:126), § Design 7 block (spec.md:181)
**Edge case:** A regression, or an incomplete fold, re-surfaces the root of a row that already carries `Discharged:`. The brief names this as the norm ("the agent will fix a round 2 finding, and that patch becomes a fixation for following review rounds", brief:8), so it is not exotic.
**What happens:** Step 4 says "first check `## Deferred — follow-up required` for a row with the same root …; if one exists, **repair that row under R2(a) instead of appending**", with disposition `deferred: D-<n> (…; repaired)`. Applied to a discharged row this yields an incoherent record: `Discharged:` asserts the fold landed at every named section, `Deferred in:` names an old round, and the finding record may never be rewritten (R2). The next round's block then does two contradictory things — step 3 accepts the `deferred: D-<n>` disposition (a discharged row is well-formed, the eighth field being optional), while the `Discharged:` verification ("every section it names carries the fold") now fails and files `routing violation: D-<n>` P0. Nothing says whether the author may remove or rewrite `Discharged:`; R2 forbids deleting the row and says nothing about deleting a field.
**Why the spec misses it:** Step 4's same-root check was added in this round to answer round-1 F-7 (duplicate rows), before `Discharged:` existed; the two additions were not composed.
**Suggested fix:** One clause in step 4: "A row carrying `Discharged:` is not a same-root target — its finding was folded. Append a new row instead, and note the superseded id in the new row's title (`… (recurrence of D-<m>)`)." Mirror one sentence in the Design 7 block so the lens does not read the recurrence as a duplicate.

### F-5: The dispositions Design 1 step 0 prescribes carry no `§` anchor and name no sections — contradicting Design 4 and the untouched 2b rule, and blinding Design 3's recount
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec § Design 1 step 0 (spec.md:86) vs § Design 4 (spec.md:142) and `skills/spec-cycle/SKILL.md:378-383`
**Edge case:** Every routing-violation fix, and in particular a ceiling-class discharge, whose "repair" is a multi-section fold.
**What happens:** Step 0 prescribes `fixed: repaired D-<n>`, `fixed: merged`, `fixed: preamble`. None carries a `§` anchor, but the 2b prose this spec leaves in place requires "always **with a spec § anchor** the reviewer can verify" (`SKILL.md:382-383`), and Design 4 *adds* the stronger rule "a `fixed:` or `reworked:` phrase names **every** spec section the edit touched". So the spec ships a manifest contract in 2b that its own routing step's example phrases violate — the next round's reviewer, verifying dispositions against that contract, can reasonably REOPEN them as P0. Second effect: a discharge folds at every `Propagation sites` entry, but `fixed: repaired D-<n>` names none of them, so Design 3's recount — which detects a re-fold by matching a new finding's `Where` against "every section named on any `fixed:` / `reworked:` line" (spec.md:134) — is blind to discharge folds. A later finding landing on one of those sections never triggers the recount, which is the mechanism brief Decision 4 exists to provide.
**Why the spec misses it:** Step 0's phrases were written as short labels for a row-level repair; the discharge, added this round, made one of them stand for a multi-section spec edit without revisiting the label.
**Suggested fix:** In step 0: "`fixed: repaired D-<n> (§ Deferred — follow-up required)`; a **discharge** is dispositioned `fixed: discharged D-<n> — edited § <a>; § <b> (§ Deferred — follow-up required)`, naming every section the fold touched as Design 4 requires, so the recount can see them."

### F-6: The author's subject mapping is used to classify `Scope` but is not recorded in the row, so the conventions lens must re-derive it — and a disagreement is a P0
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec § Design 1 step 2 (spec.md:88), row shape `Scope:` (spec.md:118), § Design 7 block (spec.md:181), § D17 (spec.md:73)
**Edge case:** Every deferral, every round — the residue of round-1 F-6.
**What happens:** Step 2 now says "Compare by subject: map the spec section the finding lands on to the file region that section governs (this spec's own Scope-table row) and test **that region** against the brief." The mapping is a judgment call with an intermediate result — the file region — and the row's `Scope` field records only "<brief Scope-table row or Out-of-scope item cited>" (spec.md:118). The Design 7 block then asks the conventions lens to verify "by **the same subject mapping the author used**" — but the author's mapping was never written down, so the lens re-derives it independently. When the two derivations differ on a P0 row, the block's rule fires: a `Scope` "wrong in a way that changes the routing" is `routing violation: D-<n>`, a **P0** — a gate-blocking finding produced by two agents disagreeing about an unrecorded intermediate.
**Why the spec misses it:** Round-1 F-6 asked for the mapping rule and for the citation to name both sides ("Cite both: `in-scope — spec Scope row <path>; brief Scope row <path>`"); the rule was applied to step 2, the two-part citation was not applied to the field.
**Suggested fix:** Make the field carry the mapping: "`**Scope:** in-scope | out-of-scope — <file region this spec's Scope table maps the section to>; <brief Scope-table row or Out-of-scope item cited>`" (spec.md:118), and in the Design 7 block: "the lens checks the author's stated file region against the brief; it does not re-derive the mapping. Only a stated region that is itself wrong is a routing violation." Design 5's scope token rule (token before the **first** em dash) is unaffected.

### F-8: R2(c) discharge is undefined when every `Propagation sites` entry is marked `(removed round n)`
**Severity:** P3
**Where:** spec § Design 2 R2(b)/(c) (spec.md:126), § Design 7 block (spec.md:181)
**Edge case:** An in-scope-P0 row whose sites were all renamed away or removed by later rounds — R2(b) allows every entry to carry a marker, and "a row carrying any marker is exempt from the at-least-one-existing-site test".
**What happens:** R2(c) says "fold the finding at every site on its `Propagation sites` list" — there is no site left to fold at, so the author cannot produce a `Discharged:` value the lens can verify ("every section it names carries the fold"). The row stays a ceiling violation with no executable remedy: the round-1 deadlock, reached through a rarer door. It degrades to "operator drops the row by hand" (spec.md:77), which the loop never solicits.
**Why the spec misses it:** R2(b) and R2(c) were written in the same edit but not composed — (b) can empty the list that (c) consumes.
**Suggested fix:** One clause in R2(c): "If every `Propagation sites` entry is marked `(removed round <n>)`, the fold has nowhere to land: redo Design 1 step 1 for the row's finding against the current spec, append the new sites to `Propagation sites` (an R2(b)-class edit), and discharge against those."

### F-9: R6 renumbering leaves a stale `D-<n>` inside the finding *title* the next manifest copies verbatim
**Severity:** P3
**Where:** spec § Design 2 R6 (spec.md:130), § D13 (spec.md:57), `SKILL.md:378-381`
**Edge case:** A duplicate section is merged, renumbering `D-3` → `D-7`, in the same round a prior `routing violation: D-3` finding is dispositioned.
**What happens:** R6 correctly makes the *disposition* carry the new id, but 2b requires the manifest line to carry "the title copied from the prior-round report" — and that title is literally `routing violation: D-3`. The reviewer therefore sees a line naming D-3 in the title and D-7 in the disposition, with no D-3 row in the spec, while D13 tells it to "match on `D-<n>` and the row title". Nothing tells it a title's embedded id may be stale, so REOPEN is a defensible reading and the round costs a false P0.
**Why the spec misses it:** R6's fix (correctness/R1/F-4) addressed the disposition side only; the `routing violation:` title prefix carries an id by construction (spec.md:77), which makes titles id-bearing in a way 2b never anticipated.
**Suggested fix:** One sentence in R6: "When a merge renumbers a row, a prior-round finding title embedding the old id is copied verbatim per 2b and the disposition names the new id; the manifest line reads `… — fixed: repaired D-7 (renumbered from D-3 by the R6 merge)`." Mirror half a sentence into the Design 7 block so the lens does not REOPEN on it.
