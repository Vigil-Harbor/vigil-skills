## Findings

### F-1: R2(c)'s discharge precondition excludes the rows that can actually be cited — the two operative steps and the reviewers' block all invoke it on rows it does not cover
**Severity:** P1
**Where:** spec.md:127 (§ Design 2, rule R2(c)) vs spec.md:94 (§ Design 1 step 4), spec.md:86 (§ Design 1 step 0), spec.md:182 (§ Design 7 block)
**Claim:** R2(c) — "**discharging** a row whose `Finding` severity is `P0` and whose `Scope` is, or becomes under an (a) repair, `in-scope` — whether the reviewers surfaced it as a ceiling-class `routing violation: D-<n>` or as the underlying in-scope P0 citing the row: fold the finding at every site …". Step 4 — "If the finding cites a row `D-<n>` (the in-scope-P0 exception in the reviewers' block), the fold **is also that row's discharge under R2(c)**". Block — "A row cited when an in-scope P0 was filed under the exception **must carry `Discharged:` by the next round**; if that P0 was folded and the row still carries none, that is the `routing violation: D-<n>` this block files."
**Why this is wrong:** The three invocations trigger on *citation*; R2(c) triggers on *row state* (`Finding` P0 **and** `Scope` in-scope). Those sets barely overlap, because the ceiling guarantees a legitimate row never records an in-scope P0. Step 3 (spec.md:89-93) admits exactly three kinds of row: out-of-scope at any severity (including **P0**), in-scope P1, and — via the recount, spec.md:138 — a reverted non-in-scope-P0 finding. D14 (spec.md:61) and the block (spec.md:182) then let a lens file an in-scope P0 citing *any* well-formed row whose root matches, and the block is explicit that the lens's own scope call is independent of the row's: "That is different from classifying your own candidate: every lens decides for itself whether a P0 it is about to file is in-scope." So the mainline citing case is a row recording **out-of-scope P0** or **in-scope P1** — and for those, R2(c)'s stated precondition is false while step 4 orders the discharge anyway.

Three consequences, in order of cost:
1. **A P0 with no matching remedy.** If the author reads R2's "the only edits the skill makes to an existing row are (a) … (b) … and (c) …" as the fence it is worded as, the discharge is not permitted and the row keeps no `Discharged:`. The block's citation sentence then fires next round: a P0 `routing violation: D-<n>`. Step 0 (spec.md:86) enumerates four remedies — field repair (this violation names no field), R6 merge, preamble insert, "for a **ceiling-class** violation, the R2(c) discharge" — and this violation is not ceiling-class (the ceiling test at spec.md:182 requires a P0 + in-scope row). Every listed remedy misses, and R2 permits none. That is the same unrepairable-P0 shape as round-1 edge-cases/F-1 and round-2 edge-cases/F-1, reached through the third door; at round 3→4 it burns the run.
2. **A stale row that becomes a spurious ticket.** Same branch, benign reading: the root is fixed, the reviewers' D14 suppression stops anyone re-filing, the row still says `Follow-up: unfiled`, and the follow-up report — "the only reminder" (spec.md:174) — tells the operator to file a ticket for work already done. R5's "the operator may drop the row by hand" is the only escape and the loop never solicits it.
3. **Divergent records.** The author who follows step 4 instead produces a well-formed, verifiable `Discharged:` row (the block's check — "every section it names carries the fold" — passes), so two conscientious authors following the same spec leave contradictory artifacts.

Nothing in the spec resolves which rule governs; R2(c)'s "or becomes under an (a) repair" covers only the case where a lens separately files a `Scope`-field violation, which the block makes optional relative to the exception branch.
**Suggested fix:** Make R2(c)'s precondition the union of the two triggers, in the one place it is stated: "(c) **discharging** a row — one whose `Finding` severity is `P0` and whose `Scope` is, or becomes under an (a) repair, `in-scope`, **or any row cited by an in-scope P0 filed under the reviewers' exception, whatever severity and scope the row itself records**: fold the finding at every site on its `Propagation sites` list in the same round and append one field …". Then extend step 0's remedy list from "for a ceiling-class violation" to "for a ceiling-class or cited-row violation, the R2(c) discharge", so the block's citation-tracking P0 has a named remedy. No other section changes; step 4, R5 and the block already read correctly against the widened condition. (Two sites, both inside the same 2e insertion — a fold, not a defer, under this spec's own step 3.)

### F-3: Round 4 defines a title suffix for a rejection and for a fold, but not for the disposition this ticket exists to add
**Severity:** P3
**Where:** spec.md:100 (§ Design 1, round-4 half), spec.md:77 (§ Minor additions)
**Claim:** "There is no next manifest at round 4, so a rejection is recorded by suffixing the finding's title in the 2f halt block with ` — rejected: <reason>`, and a fold with ` — folded § <section>`." The roll-up repeats: "at round 4 there is no next manifest, so a rejection or fold is recorded as a suffix on the finding's title in the 2f halt block."
**Why this is wrong:** D15 (spec.md:65) and the round-4 passage (spec.md:100) both explicitly permit "appending a row routed this round (step 4 of the routing step …)" at round 4 — so a **defer** is a legal round-4 disposition, and it is the only one of the three the ticket adds. It gets no suffix. The finding still counts in `total_p0p1` (the gate is untouched, and round 4's reviewers already emitted it), so it appears verbatim in the halt block's "Remaining P0/P1" list with nothing indicating it was routed; the operator has to correlate it by title against the FOLLOW-UPS block rendered a few lines below. The two other round-4 dispositions were given suffixes precisely to avoid that correlation step (`SKILL.md:557-558` uses the same device for grilled findings: "each dispositioned title suffixed ` — grilled (spec edited; not re-reviewed)`").
**Suggested fix:** Add the third suffix in both places: "…, a fold with ` — folded § <section>`, and a deferral with ` — deferred: D-<n>`." One clause each, inside insertions this spec already makes.

### F-4: R2's "the only edits the skill makes to an existing row" is stated as exhaustive but R6 renumbers rows
**Severity:** P3
**Where:** spec.md:127 (rule R2) vs spec.md:131 (rule R6), spec.md:65 / :100 (D15's round-4 permission list)
**Claim:** R2 — "The only edits the skill makes to an existing row are (a) … (b) … and (c) …". R6 — "the author merges the later sections into it in the same round, **renumbering colliding `D-<n>` ids** from the highest in the merged section".
**Why this is wrong:** Renumbering rewrites the `### D-<n>:` heading of an existing row and is not (a), (b) or (c). The spec elsewhere treats it as a separate class — D15's permitted round-4 edits read "R2's **three** row edits — repairing the field a `routing violation: D-<n>` names, re-anchoring, and discharging — inserting a missing preamble, and **R6's merge**" (spec.md:100), which is the correct enumeration. R2's absolute wording is the outlier. Harmless to the gate (the Design 7 block already accommodates renumbering — "A disposition marked `renumbered from D-<m>` names the row by its new id"), but R2 is the rule an author consults before touching a row, and an author who reads it as a fence would decline the R6 merge that R6 mandates.
**Suggested fix:** In R2, "The only edits the skill makes to an existing row are (a) …, (b) …, (c) …, and the id renumbering rule R6's merge requires."
