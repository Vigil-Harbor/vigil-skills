### F-1: An in-scope P0 deferral row is an unrepairable, undeletable permanent routing violation — the gate can never go green
**Severity:** P0
**Where:** `C:\Users\zioni\Documents\Vigil-Harbor\vigil-skills\docs\specs\TODO\VHS-37.spec.md`:148 (Design 7 block) with :99 (R2) and :102 (R5)
**Edge case:** A row exists whose `Finding:` severity is `P0` and whose `Scope:` is `in-scope`. Two realistic paths reach this state: (a) the author mis-routes; (b) — the likely one — a row deferred as `out-of-scope` in round 1 is re-classified by the conventions lens in round 3 (Decision 6 / D17 exist precisely to make the reviewer verify `Scope`), or the brief is edited between invocations and the cited Scope row now covers it.
**What happens:** Deadlock; the loop burns all four rounds and halts red on an unresolvable P0.
- Design 7 files it: "A row whose `Finding` severity is `P0` and whose `Scope` is `in-scope` is itself a routing violation **whatever else it satisfies** … file it once, as a P0 titled `routing violation: D-<n>`".
- R2 (:99) forbids the only two exits: "`/spec-cycle` never deletes a row" and "The finding record — `Finding`, `Deferred in`, `Suggested fix` — is never rewritten." So the author can neither drop the row nor lower the recorded severity.
- The one permitted repair, R2(a) "repairing the field a `routing violation: D-<n>` finding names", does not help: the sibling clause for a mis-classified scope names the `Scope` field, and repairing `Scope:` to `in-scope` **creates** the in-scope-P0 violation. One clause's prescribed repair produces the state the other clause forbids, with no defined resolution.
- R5 (:102) closes the last door: "if a later fold happens to resolve a deferred finding's root, **the row stays**". So even folding the finding at every site leaves the violating row in place, and the next round files the same P0 again.

The only escape in the whole spec is "the operator may drop the row by hand" (R5, :102) — an out-of-band action that the loop never solicits, and that is not reachable before the 2f halt after round 4.
**Why the spec misses it:** This is a new variant of the root the run-1 hand-patch closed. run-1/edge-cases/F-1 asked for "an in-scope P0 row is itself a routing violation"; the patch added the detection but no discharge path, and it landed in a rule system (R2 no-delete, R2 no-rewrite-of-the-finding-record, R5 row-stays) that had been written on the assumption that a row is immortal. Detection plus immortality is a deadlock.
**Suggested fix:** In R2, add a third permitted edit and make Design 7 honor it, e.g.: "(c) **Withdrawing** a row whose finding the ceiling requires be folded: the author edits every site on the row's `Propagation sites` list, then appends `**Withdrawn:** folded round <n> — § <a>; § <b>` to the row. The finding record is still not rewritten." Then amend the Design 7 sentence to `A row whose Finding severity is P0 and whose Scope is in-scope, and that carries no **Withdrawn:** field, is itself a routing violation …`, and add to R5 that a withdrawn row is excluded from Design 5's render. Also state in Design 7 what the author must do when the conventions lens flips a row's `Scope` to in-scope on a P0 row (repair `Scope`, then withdraw-and-fold in the same round), so the two clauses cannot be satisfied only in sequence.

### F-2: Design 5 inserts the same block at two exits, but checklist row 8 asserts one of its literals appears once

**Where:** spec.md:123-136 (Design 5) vs spec.md:165 (Test plan row 8)
**Edge case:** Not an input edge — a straight internal contradiction that the implementer hits on the first verification pass.
**What happens:** Design 5 says "**One block** … rendered from `## Deferred — follow-up required`", shows a `text` fence containing `- D-1 … — Follow-up: unfiled`, and then names two insertion points: "inserted into the 2f halt block after the `Reviews at:` line" and "inserted into the Phase 3 block … before `=== NEXT ===`". Then restate row 8 as `grep -cF '— Follow-up: unfiled'` → 1 with an explicit "(the example lives once, under 2f)" note, and add a row asserting the extraction rule's literal (e.g. `grep -cF 'malformed row — see § Deferred'` → 1).

### F-3: The section-extent grammar guards blockquotes but not fenced code blocks — the rule mis-fires on this very spec
**Severity:** P1
**Where:** spec.md:78 and :133 (extent grammar), :148 (Design 7 duplicate-section rule), :103 (R6), :51 (minor-additions bullet)
**Edge case:** A spec whose prose quotes the heading `## Deferred — follow-up required`, or any `## `-leading line, inside a fenced code block.
**What happens:** Every statement of the grammar handles exactly one escape — "a line prefixed `> ` is never a heading and never a row" — and none mentions ``` fences. Consequences, in order of severity:

1. **False duplicate-section P0 plus a destructive merge instruction.** Design 7: "If the heading appears more than once, file a P0 titled `routing violation: duplicate section`." R6 (:103): "the author **merges** the later sections into it in the same round, renumbering colliding `D-<n>` ids". `VHS-37.spec.md` already carries `## Deferred — follow-up required` at line 81 **inside the ```markdown fence of Design 2**. The moment this spec (or any successor spec about spec-cycle) also carries a real deferral section, the reviewers file a bogus P0 and R6 instructs the author to merge Design 2's shape example into the live section — silently destroying the spec's own row-shape documentation.
2. **A false `routing violation: D-1` today.** Run the Design 7 block against the current `VHS-37.spec.md` as written: the heading is found at :81; the first non-blank content under it is the `>` preamble at :83 and it contains `must not implement anything in this section`, so the preamble check passes; the scan then treats `### D-1: <title copied from the finding>` (:85) as a row; its `Propagation sites` is `§ <a>; § <b> (new); …`, and `§ <a>` names no existing section and carries no marker, so "at least one names a section that exists" fails → P0 `routing violation: D-1`. The rule the spec ships mis-fires on the spec that documents it, on the first round it is installed.
3. **Early termination.** A fenced block containing a `## `-leading line placed after the deferral heading truncates the section, dropping every row below it from both the well-formedness scan and Design 5's render.
**Why the spec misses it:** The minor-additions bullet (:51) shows the author reasoned about exactly one escape — "so a copied heading inside a row cannot end it" — and generalized from the `Suggested fix` blockquote, which is the only place a copy was expected. Nothing anticipated a copy in the spec's own *prose*, which is guaranteed for meta-specs and common in this repo's prose-spec style.
**Suggested fix:** Add the fence to the grammar in all three places it is stated (Design 2 :78, Design 5's extraction rule :133, and the Design 7 block :148), in one clause reused byte-identically: "A line inside a fenced code block (between matching ``` or ~~~ fences, counted from the top of the file) is never a heading, never a section terminator, and never a row — the same exclusion the repo's `lint.py` applies (`lint.py:_lint_intent`, `in_fence`)." Add a checklist row: `grep -cF 'inside a fenced code block' agents/spec-reviewer-*.md` → 1 per file.

### F-4: Design 3's revert must write a row from a finding whose text D16 forbids retrieving
**Severity:** P1
**Where:** spec.md:110 (Design 3, revert bullet) vs :49 (D16) and :85-93 (row shape)
**Edge case:** A round-3 finding lands on a section a **round-1** fold touched; the recount fires; the round-1 fold is reverted and the round-1 finding is deferred as a row.
**What happens:** The row is unfillable, so the author writes a malformed row, and the next round files `routing violation: D-<n>` — the loop this ticket exists to break, now triggered by the ticket's own mechanism.

The row shape (:85-93) requires, for the *original* finding: `Finding:` (id + severity), `Where:` (section + "anchor as the reviewer gave it"), and `Suggested fix:` — "**verbatim**, as a blockquote — every line of the reviewer's text prefixed `> `, otherwise unedited". Where does that text come from?
- Not the manifest: 2b (`SKILL.md:378-383`) carries only "finding ID, severity, the title copied from the prior-round report, then a concise disposition phrase". Design 3's revert line (:110) likewise carries id, severity, title, disposition — no body, no `Where`, no fix text.
- Not disk: D16 (:49) ends with the flat, unscoped sentence "**No round directory is scanned.**"
- Not context: by round 3 the round-1 report body is two rounds and several thousand lines of spec revision back; the repo's own compaction discipline (global CLAUDE.md, "when compacting, always preserve: … modified files, test commands, ticket IDs, spec/brief paths") does not preserve reviewer finding bodies.

Secondary: for a revert the row's `Deferred in: round <n>` is ambiguous — the round the finding was raised (*m*) or the round it was deferred (*N*)? The revert manifest line is round-qualified with *m*, and the `Finding:` field records `R<m>`, so `Deferred in:` reads naturally as *N* — but nothing says so, and Design 7 checks only that the field is present.
**Why the spec misses it:** D16 was written to bound *fold detection* across invocations ("On a re-run there is no in-context fold record, so the recount does not run at all"), and its closing sentence over-generalizes into an absolute prohibition that Design 3's own row-writing needs violated.
**Suggested fix:** Scope D16's last sentence and give Design 3 an explicit read: replace "No round directory is scanned." with "No round directory is scanned **to detect a fold** — fold detection is manifest-and-context only. When a revert does fire, the author reads `docs/specs/TODO/<TICKET-ID>.reviews/round-<m>/<lens>.md` to copy the original finding's `Where` and `Suggested fix` verbatim into the row; if that report is missing or unparseable, the recount resolves by folding again with the corrected site list (the `(recount: …)` suffix path) rather than reverting." Add to the row shape: "`Deferred in:` is the round the row was appended; for a revert row that is the recount round, not the round the finding was raised."

### F-5: Design 1 step 2 has no behavior for a brief with no Scope table or no Out-of-scope list
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec.md:62 (Design 1 step 2), :92 (row `Scope:` field), :148 (D17 verification clause)
**Edge case:** The brief lacks `## Scope` or `## Out of scope` (or has them under a synonym).
**What happens:** Step 2 is defined only positively — "*in-scope* when the finding's `Where` and its `Suggested fix` fall inside **a row of the brief's Scope table** and outside every item of its Out-of-scope list; *out-of-scope* otherwise. **Cite the row or item.**" With no table, nothing can fall inside one, so the literal reading yields `out-of-scope` for everything, which is the permissive branch of the ceiling: "two or more sites and out-of-scope → **defer**, whatever the severity" — the in-scope-P0 fold mandate is disabled outright. And the mandatory citation has no referent, so every row's `Scope:` field is unverifiable and the conventions lens (D17) has nothing to verify against.
**Why the spec misses it:** SKILL.md already handles missing brief headers elsewhere (`## Brief-section parsing rules`, `SKILL.md:672`: "If a header is missing, render a single fallback bullet"), so the possibility is known to the skill; Design 1 was written against a well-formed brief and inherited none of that tolerance.
**Suggested fix:** Add to step 2: "If the brief has no Scope table, or no Out-of-scope list, classify **in-scope** and cite `brief: no Scope table` / `brief: no Out-of-scope list`. The safe default is in-scope: it can only force a fold, never permit a deferral the ceiling would forbid. A row carrying such a citation is well-formed; the conventions lens verifies only that the cited absence is real."

### F-6: `Where` names a spec section; the brief's Scope table names files — no mapping rule is given
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec.md:62 (Design 1 step 2), brief.md:14-24 (Scope table)
**Edge case:** Every finding, every round. The two sides of the comparison are in different coordinate systems.
**What happens:** A finding's `Where` is `spec § Design 3` or `spec.md:110`; the brief's Scope-table rows are file paths and file regions (`skills/spec-cycle/SKILL.md §2e (:426-434)`, `agents/spec-reviewer-*.md`). A finding about a spec *section* never literally "falls inside a row of the brief's Scope table". Under a literal reading, essentially every spec-internal finding classifies **out-of-scope**, and the ceiling's permissive branch — "two or more sites and out-of-scope → defer, whatever the severity" — then admits deferring P0s. The in-scope-P0 fold mandate, which the brief's Decision 2 calls "the one thing a spec cannot ship as a known issue", becomes unreachable in practice. The intended reading is clearly semantic (does the finding's *subject matter* fall within what the brief scoped), but two different agents — the author routing and the conventions lens verifying — must arrive at the same translation with no rule to share, and a disagreement between them is exactly the `routing violation: D-<n>` P0 that F-1 shows has no exit.
**Why the spec misses it:** Both the brief (Decision 6) and the spec state the comparison at a level of abstraction where the mismatch is invisible; it only surfaces when you try to execute it on a concrete finding.
**Suggested fix:** One sentence in step 2: "Translate before comparing: a spec-internal `Where` is mapped to the file region the spec section governs — the Scope-table row of *this* spec that the section belongs to — and that file region is what is checked against the brief's Scope table and Out-of-scope list. A finding whose `Suggested fix` would add behavior no brief Scope row and no spec Scope row covers is out-of-scope. Cite both: `in-scope — spec Scope row <path>; brief Scope row <path>`." Mirror the sentence in the Design 7 block so the conventions lens verifies against the same rule.

### F-7: A malformed row and its re-filed finding produce both a repair and a duplicate row, with no merge rule
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec.md:99 (R2), :68 (Design 1 step 4), :148 (D14 suppression clause)
**Edge case:** A row is not well-formed — the near-certain case being a round-4 row, which D15 (:48) states is "verified by the Deferred-findings block on **the next invocation's** round 1", i.e. never verified in the invocation that wrote it.
**What happens:** On the next invocation's round 1 the reviewers do two things: file `routing violation: D-<n>` P0, **and** re-file the original finding — because D14's suppression is conditioned on the row being *well-formed* ("Do not file a P0/P1 whose root is a well-formed row"). The author then receives two instructions that collide: R2(a) says repair the field the violation names (keeping row `D-<n>`), and Design 1 step 4 says the re-filed finding, if the ceiling defers it, gets "a row" — a *new* `D-<m>` for the same root. Nothing in R1, R2, or step 4 says to check whether a row for this root already exists, and R2 forbids deletion, so the duplicate is permanent: the operator files two follow-up tickets for one defect, and Design 5's render lists both.
**Why the spec misses it:** D14 correctly gates suppression on well-formedness (a malformed row must not silently swallow a finding), but nothing was added on the *producer* side to route the re-filed finding back into the existing row instead of a new one.
**Suggested fix:** Add to Design 1 step 4: "Before appending, check `## Deferred — follow-up required` for a row with the same root (same section in `Where`, same defect). If one exists, do not append: repair that row under R2(a) and disposition the finding `deferred: D-<n> (§ Deferred — follow-up required; repaired)`." Add the mirrored allowance to R2(a) so repairing a row in response to a re-filed finding — not only in response to a `routing violation:` finding — is a permitted edit.

### F-9: A blank line inside the `> `-quoted `Suggested fix` breaks the blockquote, and round-4 rows are never re-verified
**Severity:** P2
**Where:** spec.md:89-90 (row shape), :51 (minor-additions bullet), :148 (well-formedness test)
**Edge case:** A reviewer's `Suggested fix` spans more than one paragraph — routine for this lens; several fixes in this very report do.
**What happens:** The shape says "every line of the reviewer's text prefixed `> `, otherwise unedited". If the author emits blank lines *unprefixed* (the natural rendering, and what most markdown tooling produces), the blockquote terminates mid-field. Any subsequent `## `-leading line in the quoted text (common when a fix quotes a heading or a markdown snippet) then terminates the whole section per the grammar — `Propagation sites`, `Scope`, and `Follow-up` fall outside it, along with every later row. The well-formedness test catches this next round as a missing-field routing violation, so the failure is loud — **except at round 4**, where D15 (:48) defers verification to the next invocation and no reviewer runs again. A round-4 truncation is therefore visible only as `?` columns in the 2f render, or as rows the render never finds at all, and Design 6's tripwire ("a spec that carried rows in a prior round and renders `(none)` now") does not fire on a *partial* truncation. This is also the one place the spec transforms a reviewer's text on the way in (:51), so nothing else can restore it.
**Why the spec misses it:** The blockquote is used both as verbatim storage and as the grammar's escape; the spec states the prefixing rule but never states the invariant it must preserve or checks it.
**Suggested fix:** In the row shape, make the rule unambiguous: "every line, **blank lines included**, is prefixed `> ` (a blank line is stored as a bare `>`)". Add to the Design 7 well-formedness test: "every line between the `**Suggested fix:**` label and the `**Propagation sites:**` label begins with `>`; a row that breaks that is not well-formed." Both are single-site edits.

### F-10: Routing-violation findings are not exempt from routing, so the enforcement mechanism can be deferred by its own rules
**Severity:** P2
**Where:** spec.md:59 ("Route **every** P0 and P1 finding"), :67 (ceiling), :99 (R2(a))
**Edge case:** A `routing violation: D-<n>` P0 whose repair touches two places — e.g. the row *and* the preamble, or two rows after an R6 merge renumbering.
**What happens:** Design 1 opens with "Route **every** P0 and P1 finding to exactly one disposition", with no carve-out. A routing-violation finding's `Where` is `§ Deferred — follow-up required` — a section of the spec that no brief Scope row covers, so under F-6's unresolved mapping it classifies out-of-scope; two or more sites plus out-of-scope routes it to **defer**. The result is a new row recording that an existing row is malformed. On the following round D14 suppresses the re-file (the new row is well-formed), the malformed row is never repaired, and the gate can go green carrying a broken deferral record whose only surface is `?` columns in the follow-up report. R2(a) clearly intends repair to be the disposition, but it is written as a permission ("the only edits the skill makes"), not as a routing rule that overrides the ceiling.
**Why the spec misses it:** R2 and Design 1 were written as separate mechanisms; nothing states which governs a finding that is *about* the deferral machinery.
**Suggested fix:** Add to Design 1 step 0 (or as step 3's first clause): "A finding whose title begins `routing violation:` is never deferred: it is folded by the R2 repair, whatever its site count or scope. Disposition it `fixed: repaired D-<n>.<field>`." Mirror one sentence in the Design 7 block so the reviewers can verify the constraint.

### F-11: No size bound on any row field — the fix for spec bloat appends unbounded verbatim reviewer text to the spec
**Severity:** P3
**Where:** spec.md:89-91 (`Suggested fix`, `Propagation sites`), :38 (Decision 8), :193 (Out of scope 5)
**Edge case:** Persistence checklist item 2. Several long findings deferred over a run, or across invocations sharing one spec.
**What happens:** `Suggested fix` is stored verbatim with no truncation and no length cap; `Propagation sites` has a floor of two entries and no ceiling; R2 forbids ever rewriting the finding record, so a row only grows (re-anchor markers append). The section is re-read in full by the author and by four reviewer agents every round, and the spec is carried in every reviewer's context. Decision 8 and Out-of-scope 5 fence a cap on the *number* of rows; neither addresses per-row size, so this is not the same fenced question.

**Suggested fix:** Either accept it explicitly in `## Out of scope` ("no size bound on a row; verbatim provenance is worth the bytes"), or bound it in the row shape: "`Suggested fix` is stored verbatim up to 40 lines; beyond that, store the first 40 lines followed by `> … (truncated; full text at docs/specs/TODO/<TICKET-ID>.reviews/round-<n>/<lens>.md § F-<k>)`." The second also gives F-4's revert path a stable pointer.

### F-12: Persistence residue — concurrent `D-<n>` allocation and row schema-version skew are undocumented
**Severity:** P3
**Where:** spec.md:98 (R1), :148 (well-formedness "all seven fields")
**Edge case:** Persistence checklist items 5 and 6.
**What happens:** (a) *Write-then-read race:* R1 allocates `D-<n>` as "highest already in the section", read-modify-write on a shared file. Two invocations sharing one spec both allocate the same id; the loser's row is lost with the file write. SKILL.md declares this out of the supported flow for `grill.md` only (`SKILL.md:534-538`, "Concurrent invocations sharing one reviews tree are outside the supported flow"); the deferral section is a new persisted record that inherits no such statement. (b) *Schema forward-compat:* the well-formedness test is "all **seven** fields are present". A later version that adds an eighth field turns every pre-existing row — which R2 forbids rewriting — into a permanent `routing violation` P0 on the next invocation, which is F-1's deadlock shape. Design 6 covers the inverse skew (old agents, new spec) via `python sync.py install`; the old-spec/new-agents direction is uncovered.
**Why the spec misses it:** The section is treated as spec prose rather than as a persisted record with readers on both sides of a version boundary.
**Suggested fix:** One sentence in R1: "Concurrent `/spec-cycle` invocations over one spec are outside the supported flow — `D-<n>` allocation is read-modify-write and last-writer-wins over the whole file, matching 2f-i's stated posture for `grill.md`." One in the Design 7 block: "A row missing a field this block did not require when it was written is a P2 correction, not a routing violation; only a missing `Finding`, `Propagation sites`, or `Scope` is a routing violation."
