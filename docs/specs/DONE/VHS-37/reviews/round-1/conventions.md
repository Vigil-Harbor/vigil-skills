## Findings

### F-1: Design 5 re-states the section-extent grammar instead of consuming it, and never says where that rule lands in `SKILL.md`
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec.md:133 (Design 5 "Extraction rule") vs spec.md:78 (Design 2); spec.md:18 (Scope row: 2f *and* Phase 3 "each gains the follow-up report block")
**Convention violated:** `skills/spec-cycle/SKILL.md:661` — the file's own single-source-of-truth idiom for a parse rule, written into the immediately adjacent Phase 3 block.
**Evidence:** `SKILL.md:661`: *"The Scale-declaration block consumes the `scale_lens` / `scale_target` already resolved in Phase 0 step 8 — **no re-parse of the brief.** … keeping a single source of truth for the parse (step 8)."* The spec does the opposite for the same file: Design 2 defines the extent at `:78` ("runs from its heading to the next `##` heading that is not inside a blockquote, or to end of file. A line prefixed `> ` is never a heading and never a row"), and Design 5 re-defines it at `:133` ("the section runs from its heading to the next `##` heading not inside a blockquote, or end of file"). Cross-file duplication into the four agents is justified by D11 and has precedent (VHS-15's stale-report guard is byte-identical in three agents) — this one is *inside one file* and has no such excuse. Worse, Design 5 pins landing sites only for the rendered `=== FOLLOW-UPS ===` template ("Red path: inserted into the 2f halt block…; Green path: inserted into the Phase 3 block…", and row 8 asserts `grep -cF '=== FOLLOW-UPS'` → 2) and says nothing about where the ~7-sentence extraction rule goes. An implementer reading it literally can land the parse prose twice, giving `SKILL.md` three copies of the same grammar to drift apart.
**Suggested fix:** In Design 5, replace the first clause of the extraction rule with a citation and pin the landing site: *"Extraction rule: the section's extent is as 2e defines it (Design 2) — no re-parse; the render treats every `###`-or-deeper heading in that span that is not prefixed `> ` as a row. This rule is written once, in the 2f halt block; the Phase 3 block cites it."* Optionally add a checklist row: `grep -cF 'not inside a blockquote' skills/spec-cycle/SKILL.md` → 2 (2e, 2f).

### F-2: The section grammar models markdown structure but omits fenced code blocks — the exposure the repo's two standing decisions require to be handled or named
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec.md:78 (Design 2), spec.md:133 (Design 5), spec.md:148 (Design 7 block); spec.md:185-200 (§ Out of scope, silent on it)
**Convention violated:** wiki `decisions/2026-08-25-vhs-28-validator-does-not-parse-markdown.md` (active), and the practice `docs/specs/DONE/VHS-29/spec.md` § D3 established for the residual case.
**Evidence:** VHS-28: *"A `###` subsection must terminate its parent. **A heading inside a fenced code block must *not* count as a heading.** A thematic break terminates. Setext headings exist."* — the enumeration of what section-bounding actually costs. VHS-29 D3 shows what the repo does when it declines to pay it: *"It does **not** mask fenced code blocks … The residual exposure is a fenced example entry in the header … This is accepted, not overlooked"* — named in the spec and recorded in Out of scope. This spec takes the third path: it models markdown structure (blockquote-aware headings, `###`-or-deeper rows, exact-heading matching) but excludes only blockquotes, and never names the fence case anywhere. The exposure is live in this repo, not hypothetical, because specs about `/spec-cycle` quote the shape: **this very spec puts `## Deferred — follow-up required` inside a ```markdown fence at spec.md:81**, with the preamble at `:83` and a placeholder row at `:85-93`. A reviewer executing the Design 7 block against a spec of that shape reads the fenced template as the live section, tests `Propagation sites: § <a>; § <b> (new)` against the "at least one names a section that exists" rule, fails it, and files `routing violation: D-1` as a **P0** — four lenses, on a spec that deferred nothing. That is a gate-blocking false positive on exactly the class of spec this ticket will be dogfooded against next.
**Suggested fix:** One clause, in the grammar sentence at spec.md:78 and mirrored at `:148` (and inherited by `:133` once F-1 collapses it): *"A line inside a fenced code block is never a heading and never a row."* If instead the author judges fence-awareness not worth the words, follow VHS-29 D3 rather than leaving it unstated: name the exposure in Design 2 and add an Out-of-scope item recording that a fenced example of the section shape can be misread as the section and why that is accepted.

**Pre-ship recommended:** yes
**Where:** spec.md:21 (Scope row for `docs/spec-workflow-reference.md`, `:84` and `:88` only) and spec.md:23 ("Left alone, byte-identical", which does not mention it); against `docs/spec-workflow-reference.md:81` and `AGENTS.md:101`

### F-4: The re-anchor / removal marker system is a load-bearing spec-level addition that the "minor additions" roll-up does not record
**Severity:** P3
**Where:** spec.md:99 (rule R2(b)) and spec.md:148 (the waiver in the Design 7 block), against spec.md:51 (the roll-up)
**Convention violated:** `docs/spec-workflow-reference.md:77` / `AGENTS.md` § Parallel review agents — the conventions lens classifies every decision as brief-authorized, ticket-authorized, spec-addition-with-rationale, or silent addition; plus this spec's own stated device at `:51` ("Minor additions, **recorded so the drift-check can see them**").
**Evidence:** The brief authorizes nothing about mutating an existing row — its Scope row for the section (brief:21) lists the eight fields and nothing else, and D12/R2 make `Follow-up:` the operator's field. R2(b) nevertheless grants the skill a second class of edit to an existing row: `§ <new heading> (re-anchored round <n>)` / `§ <old heading> (removed round <n>)`, marker per entry, marked entries still counting toward the two-entry floor, and a row carrying any marker exempted from the one-existing-site test — which the Design 7 block then has to waive around. That is the only sanctioned mutation of a persisted row and it drives a reviewer waiver, so it is more load-bearing than several items the roll-up does record (`(none)` render, the `routing violation:` title prefix, round-4 title suffixes). It is (c)-class, not wrong — its provenance is a prior round — but the Phase 3 drift-check reads the spec, not the review directory.
**Suggested fix:** One clause appended to spec.md:51: *"a row's `Where` and `Propagation sites` entries may be re-anchored or marked removed when a later round renames or deletes the section they name — the skill's only edit to a persisted row's location fields, and the reason the reviewers' one-existing-site test carries a waiver."*

### F-5: Decisions are a flat numbered list, not `### D<n>` subsections — the shape every recent spec in this repo uses
**Severity:** P3
**Where:** spec.md:27-51 (`## Decisions`)
**Convention violated:** `skills/spec-cycle/SKILL.md:309` — *"the spec must reflect each one with a **Decision** subsection that names it and explains how the design honors it"* — and the shape of the four most recent shipped specs.
**Evidence:** `docs/specs/DONE/VHS-36/spec.md`, `VHS-33/spec.md`, `VHS-32/spec.md`, and `VHS-29/spec.md` all use `## Decisions` + one `### D<n> — <title>` subsection per decision (VHS-36 runs D1–D11, VHS-29 D1–D7). This spec uses a numbered list for brief decisions 1–9 and bold-prefixed bullets for `D10.`–`D17.`, with a twelve-clause run-on bullet at `:51` carrying the rest. Two costs: `/spec-close` Phase 1 step 2 is written as *"For each `### Decision` in the spec: read the relevant code … and confirm the decision is reflected"*, and it will have no per-decision anchor to walk at close time; and D15/D16, which are cited normatively from Design 1 and Design 3, are body text inside a bullet rather than addressable sections. (`D10`–`D17` also sit in the same document as the row ids `D-1`, `D-2` — one hyphen apart, cited in adjacent sentences at `:48` and `:68`.)
**Suggested fix:** Promote the eight spec-level decisions to `### D10 — <title>` … `### D17 — <title>` subsections under `## Decisions`, leaving the brief-carried 1–9 list as is, and split the `:51` roll-up into a final `### Minor additions` subsection with one bullet per addition. Purely structural — no wording changes — and it makes F-4's added clause a bullet rather than a thirteenth clause.
