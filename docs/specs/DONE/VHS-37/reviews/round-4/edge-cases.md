## Findings

### F-1: The `(grill)` exemption names two of the four `Propagation sites` tests, and the placeholder value the spec authorizes fails the other two
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec § Design 7 block (spec.md:182), against § Design 1 (spec.md:96) and § Minor additions (spec.md:77)
**Edge case:** A Settled grill decision defers a finding that names no propagation site — the mainline grill case, since a multi-site finding would already have been routed to a row by round 4's own routing step. spec:96 tells the author to write `Propagation sites: § (operator decision — routing tests not run)`.
**What happens:** The block's well-formedness definition applies four distinct `Propagation sites` tests: (i) two or more entries; (ii) at least one names a section that exists in the spec; (iii) every other entry names an existing section, is marked `(new)`, or carries a re-anchor/removed marker; (iv) a re-anchored entry is checked against its new heading. The `(grill)` sentence exempts the row from (i) and from the ceiling test, and nothing else by name. The authorized placeholder fails (ii) *and* (iii) — it is not an existing section, carries no `(new)` marker, and carries no re-anchor/removed marker.

The row is saved by the sentence's trailing catch-all, "it records an operator decision and **is checked only for the presence of its fields**", which does override (ii)–(iv). So the P1 failure round 3 filed does not fire as written. What remains is that the sentence carries two rules that fully overlap — an enumeration that under-covers and a catch-all that supersedes it — and every other statement of the exemption in the spec repeats only the narrow pair: spec:77's roll-up ("exempt from the two-entry floor and the ceiling test, since routing never ran on it") and the closure manifest itself. The drift-check reads spec:77, and spec:180 lets the implementer re-lay the block as "a lead sentence plus one bullet per rule" — a bulletisation driven by the roll-up's two-item reading drops the catch-all and restores the round-3 P1: four lenses file `routing violation: D-<n>` on a row whose only in-loop repair (R2(a)) would mean inventing a propagation site.
**Why the spec misses it:** The round-3 fix was written against the *floor* (the two-entry count), which is what the finding's title named. The one-existing-site and every-other-entry tests are stated in the same sentence of the block but were not enumerated in the exemption; the catch-all was added as a closing summary rather than as the operative rule, so nothing else in the spec restates it.
**Suggested fix:** Make the enumeration complete so the catch-all is a restatement, not a rescue. In spec:182: "…is exempt from the two-entry `Propagation sites` floor, from the at-least-one-existing-site and every-other-entry tests on `Propagation sites`, and from the ceiling test; it records an operator decision and is checked only for the presence of its fields." Mirror the same three-item list in spec:77's roll-up so the drift-check and any bulletisation see it. No new checklist row needed — row 6's `(grill)` grep already covers presence.

### F-2: The `(grill)` ceiling exemption is keyed on a permanent field and survives the R2(a) repair that turns a grill row into an ordinary routed row
**Severity:** P3
**Where:** spec § Design 7 block (spec.md:182), § Design 1 step 4 Defer branch (spec.md:94), § Design 2 rule R2(a) (spec.md:127)
**Edge case:** A grill row `D-3` is appended at round 4 for a P0 (`Finding: … (P0)`, `Scope: operator — round-4 grill`). The operator re-runs (2f option 1). In round 2 of the re-run a new **in-scope P1** on the same root routes to defer, and step 4 says: "if one exists and carries no `Discharged:`, repair that row under R2(a) instead of appending." The repair writes real `Propagation sites` and replaces `Scope:` with `in-scope — <region>`.
**What happens:** The row now records **P0 + in-scope** — the one state the ceiling forbids — but `Deferred in:` still carries `(grill)`, and the exemption is keyed on that field alone, permanently. The ceiling test never fires, so the `routing violation: D-<n>` that would normally force the R2(c) discharge is never filed, and the spec can carry an in-scope P0 as a settled known issue with no in-loop signal. `Finding` severity is frozen by R2 ("the finding record … is never rewritten"), so nothing can walk the severity back down to match the new scope either.

For an ordinary row the same sequence self-corrects: out-of-scope P0 repaired to in-scope → ceiling test fires → R2(c) discharge → folded. Only the `(grill)` marker defeats it. The residual protection is D14's exception — a lens's own in-scope P0 candidate on that root is still always filed and folded — so the unshippable defect surfaces if any lens regenerates it, which is why this is P3 rather than P1. But that is the belt, and the ceiling was the braces; the spec's Decision 2 calls the in-scope-P0 fold the one rule that cannot be waived.
**Why the spec misses it:** The exemption was written for the row at the moment of its creation ("since routing never ran on it", spec:77) and keyed to the field that records that moment. The R2(a) same-root repair — the one mechanism that makes routing run on an existing row after the fact — was written in an earlier round for routed rows, and the two were never composed.
**Suggested fix:** Bound the exemption to the state that justifies it rather than to the marker. In spec:182: "The exemption holds while the row's `Scope:` still reads `operator …`; once an R2(a) repair replaces it with an `in-scope`/`out-of-scope` classification, routing has run on the row and it is checked as a routed row, ceiling test included." Add a matching half-clause to step 4's repair instruction (spec:94) so the author knows the repair re-arms the ceiling, and to spec:77.

### F-3: A cited P1/out-of-scope row that had its in-scope slice folded records nothing about the fold, and R5 covers only the full-resolution case
**Severity:** P3
**Where:** spec § Design 1 step 4 (spec.md:94), § Design 2 rule R5 (spec.md:130), § Design 5 (spec.md:167)
**Edge case:** The round-3→4 fix's new else-branch: a lens files an in-scope P0 that is the narrow, unshippable slice of a broad out-of-scope root already carried by row `D-2`; the author folds the finding at its own sites, dispositions it `fixed: edited § <a>; § <b>`, and — correctly — leaves `D-2` live.
**What happens:** `D-2` is unchanged: `Follow-up: unfiled`, no `Discharged:`, no marker of any kind. The follow-up report prints it identically to a row nothing has touched, and the report is, per § Design 6, "the only reminder". The operator files a ticket whose scope silently overlaps work already in the spec — repeatedly, since the branch can fire once per in-scope slice per round. R5 is the only rule pointed at this situation and it addresses a different one: "if a later fold happens to **resolve** a deferred finding's root, the row stays … the reviewers' existing rule records the finding CLOSED with the fold as evidence." Here the root is *not* resolved, so no closure-table entry attaches to `D-2`, and R2's freeze on the finding record plus the reservation of `Discharged:` for a full R2(c) discharge leave the author no field in which to say so. This degrades gracefully (an over-broad ticket, not a lost finding), hence P3 — but it is the one branch the round-3 fix newly created, and it is the branch with no audit trail.
**Why the spec misses it:** The round-3 fix was scoped to stopping the *wrong* record (a spurious `Discharged:`); the question of what the *right* record is for a partially-folded live row was not asked, and R5 was written before the branch existed.
**Suggested fix:** One appendable, non-destructive marker, in the class R2(b) already permits. In R2, alongside (b): "a row left live after an in-scope P0 citing it was folded may gain `**Partly folded:** round <n> — § <a>; § <b>`; it is not a discharge, the row still needs a follow-up, and the finding record is untouched." Have step 4's else-branch write it, § Design 5 print ` [partly folded: <value>]` after `Follow-up:` the way it already does for `Discharged:`, and the § Design 7 block treat the field as optional and verified like `Discharged:`. Extend R5 to name the partial case. If that is judged too many sites under this spec's own ceiling, state instead in R5 that a live row may have had slices folded and that the operator scopes the follow-up against the current spec — but say it somewhere, because today nothing does.

### F-4: A Settled grill decision carrying several `ref:` ids has no defined row cardinality
**Severity:** P3
**Where:** spec § Design 1 (spec.md:96), § Design 2 row shape (spec.md:118-121), against `skills/spec-cycle/SKILL.md:558-561`
**Edge case:** 2f-i's Settled items carry `ref:` ids in the plural — the untouched step 5 is explicit about it: "`dispositioned` lists every id on a Settled item that step 4 applied, each id once, in seed order, **however many ids one decision carried**". One operator decision dispositioning three round-4 findings as a single follow-up is therefore a reachable, documented shape.
**What happens:** spec:96 is written in the singular ("A Settled decision that dispositions **a finding** as a follow-up is satisfied by appending **a row**") and the row shape has exactly one `Finding:` field with one `(P0 | P1)` parenthetical. Two authors diverge: one appends three near-identical rows (three `D-<n>` ids, three follow-up tickets, three lines in the report for one operator decision — and no same-root guard applies, because routing's tests do not run here); the other writes one row with three ids in `Finding:`, which the render's severity parse ("the parenthetical in `Finding:`") reads as whichever parenthetical it hits first, silently mis-labelling the other two. Neither is wrong under the spec as written. Cost is a divergent artifact and a possibly wrong severity column, not a broken loop — P3.
**Why the spec misses it:** spec:96 was written from the routing side, where a finding-to-row mapping is 1:1 by construction. The grill path's `ref:` plurality lives in the untouched 2f-i region, which § Scope keeps byte-identical, so nothing prompted a re-read of its cardinality.
**Suggested fix:** One clause at spec:96: "A Settled decision carrying more than one `ref:` id appends one row per referenced finding, each with its own `D-<n>` and its own `Finding:` record; the shared decision is identified by the common `Deferred in: round 4 (grill)` and by `round-4/grill.md`." Nothing else changes — the row shape, the render and the block all already handle N independent rows.
