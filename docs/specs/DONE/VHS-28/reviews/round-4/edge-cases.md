## Findings

### F-1: The scaffold has no document title, so the newly-pinned `Previous title` line has no source — and test item 8 cannot be constructed with the specified CLI
**Severity:** P0
**Where:** spec.md:305-310 (§ `create_handoff.py`), spec.md:156-176 (D4 `TEMPLATE_SECTIONS`), spec.md:330 (test item 2), spec.md:336 (test item 8), spec.md:296 (CLI)
**Edge case:** Chaining any document produced by this skill — i.e. the ordinary case, and the exact case test item 8 builds.
**What happens:** `create_handoff.py` must emit `- Previous title: <escaped, ≤80 chars>`, read "from the previous document's first `#` heading". Nothing in the spec makes the scaffold emit a `#` heading. `TEMPLATE_SECTIONS` begins at `##` Session Metadata and has no depth-1 row, and test item 2 asserts "the scaffold's heading sequence **equals** `[name for _, name in TEMPLATE_SECTIONS if name]` in order" — so an H1 title would *fail* that assertion. Under the strict reading the matcher finds no depth-1 heading and the implementer formats `None` into a pinned line (or raises `AttributeError` on `match.group(2)`); under the loose reading ("first ATX heading") every chained document reads `Previous title: Session Metadata`, permanently constant.
**Why the spec misses it:** Round 3's correctness/F-1 fix added the consumer of the title without adding its producer. The contradiction is provable from the CLI alone: `create_handoff.py [slug] [--continues-from FILE] [--project-path PATH]` has no title argument, and the slug is sanitized to `[a-z0-9-]` and truncated to 60 chars (spec.md:300) — so a document A generated by this script can never have "a title containing `|`, backticks, and 200 characters", which is precisely what test item 8 asserts against. Separately, D3 spec.md:119-133 exposes only `has_section(normalized, name) -> bool` and closes with "That is the whole matcher surface" — a boolean cannot return a title, so `create_handoff.py` must reach for the underscore-private `_HEADING_RE` that D3 says is not part of the surface. All 23 on-disk documents carry `# Handoff: <sentence>` at line 1 (e.g. `MCP Server/.claude/handoffs/2026-08-23-154211-mcp-51-spec-cycle-5-rounds.md:1`), so the corpus expects a title the new template does not define.
**Suggested fix:** Add a depth-1 row to `TEMPLATE_SECTIONS` — `| # | *(document title)* | title |` — and state in § `create_handoff.py` what fills it (e.g. `# Handoff: <slug, de-hyphenated>`, with an optional `--title` argument if an arbitrary title is wanted). Adjust test item 2's expected sequence to include it, or state that the title row is excluded from the drift comparison. In D3, expose a named accessor (`first_heading_title(normalized) -> str | None`) so the extraction is on the declared surface, and define the emitted line when it returns `None` (`- Previous title: *(untitled)*`). If `--title` is not added, rewrite test item 8's escaping case to chain from an authored fixture rather than from a generated A.

### F-2: The `open(path,"x")` claim leaves a zero-byte `.md` in the handoffs directory on every failure path, and RESUME selects it as the newest handoff
**Severity:** P1
**Where:** spec.md:301 (collision/atomicity bullet), spec.md:279 (RESUME listing), spec.md:335 (test item 7)
**Edge case:** Partial failure between the claim and the `os.replace` — a git subprocess raising, a `--continues-from` resolution error, `Ctrl-C` during the up-to-four 10-second git calls, or any rendering exception.
**What happens:** The bullet claims the target *first*, renders to a `mkstemp` temp file *second*, and `os.replace`s *third*. The stated `finally` removes **only the temp file** ("Remove the temp file in a `finally` if rendering fails"). The claim file is never cleaned up, so a failed CREATE leaves a 0-byte `YYYY-MM-DD-HHMMSS-<slug>.md` on disk. RESUME lists `*.md` newest-first and ignores only `*.tmp` (spec.md:279) — the orphan is a `.md`, dated now, so it is the *first* candidate the agent offers, and it validates as `NEEDS WORK` with all three sections missing. A second CREATE with the same slug then also skips that name and burns a `-2` suffix. This is a persistence-checklist atomicity failure on a realistic path, which the checklist rates P1.
**Why the spec misses it:** The bullet was written to fix "os.replace clobbers", and correctly separates claiming from atomic replacement — but it treats the claim as free. It is not: on Windows the claim is an observable, durable artifact for the entire render window. Two adjacent constraints are also unstated: (i) ordering — the `--continues-from` hard-error bullet (spec.md:304) says "non-zero exit, **no document written**" and test item 7 asserts "`--continues-from` not-found and absolute-path escape both exit non-zero with **no file created**", which is only true if *all* argument validation precedes the claim, and the bullets appear in the opposite order; (ii) on Windows `os.replace` fails with `PermissionError` if the claim handle is still open, so the claim must be `with open(path, "x"): pass`, not a held handle — a POSIX-passing / Windows-failing divergence on the operator's own platform.
**Suggested fix:** In spec.md:301, state the order and widen the cleanup: "Validate `--project-path`, the slug, and `--continues-from` **before** claiming. Claim with `with open(path, "x"): pass` (the handle is closed immediately — an open handle makes `os.replace` fail on Windows). Wrap everything from the claim through the `os.replace` in `try/finally`: on failure remove **both** the temp file and the claim file, so a failed CREATE leaves the directory exactly as it found it." Give the retry cap a number rather than "a small cap". Extend test item 7's assertion from "no file created" to "the handoffs directory is byte-identical to its pre-call state after a forced rendering failure".

### F-3: The `[TODO: …]` marker is now the entire completeness gate, but its pattern is defined nowhere and lives in neither `_sections.py` nor any pinned format
**Severity:** P2
**Where:** spec.md:18 (D0), spec.md:137 (D4 module contents), spec.md:317 (§ `validate_handoff.py`), spec.md:302 (git placeholders), spec.md:323 (§ `handoff-template.md`)
**Edge case:** Any divergence between the marker `create_handoff.py` writes and the one `validate_handoff.py` looks for; and any generated section whose placeholder happens to be marker-shaped.
**What happens:** D0 promotes the TODO scan from a secondary signal to *the* completeness check, yet it is the one load-bearing string the spec never pins. Is it the literal `[TODO:`? Case-sensitive? Does `[TODO]` (no colon) or `[ TODO: x ]` count? D4 enumerates exactly what `_sections.py` declares — `TEMPLATE_SECTIONS`, `REQUIRED_SECTIONS`, `RECOMMENDED_SECTIONS`, `_HEADING_RE`, the normalizer, `has_section()` — and the marker is not among them, so the two entry points each get their own copy. That is the same shape as the defect VHS-28 was filed for (one matcher, three places, diverging), relocated onto the check D0 just made load-bearing. Concretely undefined: spec.md:302 says a git failure emits "placeholder text" distinguishing not-a-repo / no-commits / timed-out. If any implementer writes that placeholder as `[TODO: git unavailable]`, then CREATE in a non-repo directory — an explicitly supported path (test item 7) — can **never** reach `READY`, and the author must delete a line the tool generated. Conversely spec.md:323 says the template carries "every section carrying a `[TODO: …]` marker", which cannot be true of `## Handoff Chain` (spec.md:305-310 pins its content, no marker) or `### Recent Commits` (git-generated).
**Why the spec misses it:** In v1-v3 the marker was one of two completeness signals and the ≥50-char check carried the weight; the scope-down inverted that without moving the marker into the shared module.
**Suggested fix:** In D4, add `TODO_MARKER_RE` (e.g. `re.compile(r"\[TODO\b[^\]]*\]", re.IGNORECASE)`) to the `_sections.py` declaration list, and state that `create_handoff.py` renders markers through a helper from the same module. In spec.md:302 state explicitly that git-failure placeholders **must not** use the marker shape (they are diagnostics, not author work). Amend spec.md:323 to "every *authored* section"; name `Session Metadata`, `Recent Commits`, and `Handoff Chain` as generated and marker-free.

### F-4: With the length check gone, completeness fails open for every document `create_handoff.py` did not scaffold — and for the natural way authors clear a marker
**Severity:** P2
**Where:** spec.md:18 (D0), spec.md:22-26 (D0 accepted limits), spec.md:199 (D6 `NEEDS WORK`), spec.md:331 (test item 3)
**Edge case:** A legacy or hand-written handoff; or an author who *deletes* the placeholder line instead of replacing it.
**What happens:** `READY` requires three headings present, no marker, no secret. A document with `## Current State Summary`, `## Important Context`, `## Immediate Next Steps` and **zero bytes of content under any of them** validates `READY`, exit 0. Deleting a `[TODO: …]` line is indistinguishable from filling the section — and deletion is the cheaper action, the one D0 itself recommends for the false-positive case ("clearable by rewording", spec.md:24). Every one of the 23 real corpus documents already carries zero `[TODO` markers, so on the entire existing corpus the completeness check is a no-op and only the three presence checks fire. D0's claim that the marker scan "already answers completeness — better than a character count" is therefore true only for the narrow window between scaffold generation and first edit, on documents this script produced.
**Why the spec misses it:** D0 argues the marker is a *better* completeness proxy than length, and the accepted-limits list (spec.md:22-26) records only the three false-verdict cases, not the class of documents for which the check does not apply at all.
**Suggested fix:** Add a fourth bullet to D0's accepted limits, stated plainly: "Completeness is checked only where a marker survives. A section left empty, or one whose marker was deleted rather than replaced, validates `READY`. Documents this skill did not scaffold — legacy and hand-authored — get presence checking only. Accepted: the gate is an author's checklist, not an adversarial validator." That is a one-paragraph honesty edit, and it also makes the § Deferred human-check item (F-7) accurate.

### F-5: A `[TODO: …]` left in a *recommended* section is a hard `NEEDS WORK`, while deleting that section outright is `READY` — the gaming incentive D6 exists to remove
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec.md:199 (D6 verdict table), spec.md:205 (D6 "informational only"), spec.md:317 (§ `validate_handoff.py` check order)
**Edge case:** A scaffold where the author fills the three required sections and leaves `### Potential Gotchas` untouched — the common case, since six of the nine sections are optional.
**What happens:** `NEEDS WORK`/exit 1, because the TODO scan is whole-document and D6's `NEEDS WORK` row reads "a required heading absent, **or** a `[TODO: …]` remains" with no scope qualifier. Meanwhile spec.md:205 says a *missing* recommended section "prints as informational lines and changes nothing". So the author who deletes `### Potential Gotchas` and its placeholder ships green, and the author who leaves it visible as an honest "nothing here yet" is blocked. That trains exactly the deletion behavior D6's own rationale objects to ("teaches authors to flatten headings until the number moves", spec.md:194).
**Why the spec misses it:** The TODO scan was whole-document when it was one signal among several; as the sole completeness gate its scope now decides verdicts.
**Suggested fix:** One row-level edit in D6: markers under a `RECOMMENDED` heading print as informational lines like a missing recommended section, and only markers outside a recommended section produce `NEEDS WORK`. (This requires knowing which heading a marker sits under — if that is too close to the sectioning D0 refuses, take the simpler branch: keep the scan whole-document and state in D6 that leaving a recommended placeholder is deliberately treated as unfinished work, so authors know the rule rather than discovering it.)

### F-6: The new bare-path chain rule follows a link the author explicitly disclaimed — three corpus documents write the predecessor path *inside a "None"*
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec.md:281 (RESUME, chain following)
**Edge case:** A `Continues from` line whose text is a negation that happens to quote a path.
**What happens:** The rule is "**If the line carries no href** — two on-disk documents record a bare backticked path instead — take the first backticked or bare path on the line". Three corpus documents carry no href *and* a path, and in all three the surrounding prose is a disclaimer:
- `MCP Server/.claude/handoffs/2026-08-22-182013-mcp-52-spec-cycle-halted-red.md:18` — ``- **Continues from**: None. The scaffold auto-linked `2026-08-15-060410-mcp-45-post-merge.md` `` — path on the same line, so the rule follows it and RESUME silently reads an unrelated MCP-45 handoff as this session's predecessor, presenting stale context as chain context.
- `Petasos/.claude/handoffs/2026-08-09-192407-pet-176-spec-cycle.md:18-20` — "None. (The scaffold auto-linked / `<path>`; that is **unrelated** … and should be ignored.)" — path on the *next* line, so the rule stops for the right reason by accident.
- `Primer/.claude/handoffs/2026-08-23-013031-renderer-spike-and-storyboard.md:18` — "**None — this is a new thread.** The scaffold auto-linked" — same shape.

The two genuine bare-path links the rule was written for are real and correctly counted (`Primer/…2026-08-06-192609-pri4-royal-ink-shipped.md:21`, `Zoho inventory/…2026-08-22-infuzd-capability-menu-and-pricing.md:6`), so the "two on-disk documents" claim is accurate — the rule just has no way to tell those two from the three negations.
**Why the spec misses it:** The rule was derived from the two positive instances; the negation instances share the same syntactic precondition (no href) and were not sampled. Since RESUME is agent-executed prose and deliberately untested (spec.md:341), nothing catches it.
**Suggested fix:** One clause in spec.md:281: "…take the first backticked or bare path on the line **unless the text preceding it on that line contains `None` or `new thread` — three on-disk documents record a rejected auto-link that way, and following it resumes from the wrong session.** If neither yields an existing file, note it and stop the chain rather than guessing."

### F-8: D0's second accepted limit is characterized as requiring deliberate authorship; the realistic trigger is quoting another handoff
**Severity:** P3
**Where:** spec.md:25 (D0 accepted limits)
**Edge case:** A handoff that pastes an excerpt of a previous handoff into a fenced block — squarely this skill's domain — or one that comments a section out with `<!-- … -->`.
**What happens:** The limit reads "it requires deliberately writing a required section name as a code comment". It does not: every corpus document contains `## Current State Summary`, so pasting any of them into a fence carries that heading along, and the presence check passes for a section the author never wrote. The same is true of a required heading inside an HTML comment block, which is how an author most naturally "removes" a section they will fill later — the line still starts with `##` and still matches. Neither shape is deliberate, and both produce a false `READY`.
**Why the spec misses it:** The limit was reasoned from the fence case only, where "someone typed a section name as a code comment" is indeed rare.
**Suggested fix:** Restate as: "A required section name appearing anywhere on a line that starts with 1-6 `#` satisfies that presence check — including inside a fenced block, an indented-under-4-spaces block, or an HTML comment. Handoffs quoting other handoffs will hit this. It is a false *pass*, never a false fail, and the author is the reader of the verdict." Optionally add a fenced-quote case to test item 5 alongside the two already pinned.

### F-9: `cwd=` alone does not redirect git when `GIT_DIR`/`GIT_WORK_TREE` are set in the environment
**Severity:** P3
**Where:** spec.md:298 (§ `create_handoff.py`, `--project-path`)
**Edge case:** `create_handoff.py` invoked from a process that exports `GIT_DIR` or `GIT_WORK_TREE` — a git hook, a `git` alias wrapper, or a shell where a prior command exported them.
**What happens:** git resolves those environment variables ahead of repository discovery from `cwd`, so the document is pre-filled with the *other* repository's branch and commits — the precise failure the round-3 `cwd=` fix was made to eliminate, reappearing through a different channel. Silent: the placeholder logic never fires because git succeeds, just against the wrong repo.
**Why the spec misses it:** The fix targeted the process working directory, which is the dominant case; the environment channel is the remaining one.
**Suggested fix:** Extend spec.md:298: "…and the working directory of every git subprocess (`cwd=<resolved project path>`, with `GIT_DIR` and `GIT_WORK_TREE` removed from the child environment so `cwd` alone determines the repository)."
