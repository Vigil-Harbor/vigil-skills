### F-1: the oldest-first harvest bound can defer the incremental review out of 6a's own harvest set, and the round still reports `verdict-landed` / "no new findings"
**Severity:** P1
**Where:** spec § D2 2b step 2 (spec.md:924-942), § D5 outcome rules (spec.md:1282-1308), § Decision 14 (spec.md:673-682)
**Edge case:** any 6a poll where more than 10 body-carrying reviews sit above `LAST_BODY_REVIEW_ID` — the first run against a mature PR, which Decision 2 (spec.md:106-108) explicitly contemplates, or any run whose mark is stalled (F-2 below).
**What happens:** silent false negative on the exact review the step exists to catch. Worked example, 25 body-carrying reviews on the PR: Step 2 harvests the 10 oldest and advances `LAST_BODY_REVIEW_ID` to the 10th; round 1 pushes and enters 6a. The candidate set is reviews 11–25 plus CodeRabbit's just-posted incremental review 26. 2b step 2's bound takes the **10 oldest**, so the harvest set is 11–20 and review 26 is *deferred*. `new_body_items` now counts only harvest-set items with `submitted_at > PUSH_TIME` (spec.md:1282-1284) — reviews 11–20 are all pre-push, so the count is **0**. `NEW_INLINE` is 0 (the finding is body-only). The verdict stream, which is *not* bounded, returns review 26 as its highest-id record with `state != "COMMENTED"` and `submitted_at > PUSH_TIME` — so the second outcome rule fires: `REVIEW_SIGNAL=verdict-landed` (spec.md:1297-1300), which the skill's honesty rule at `:370-377` licenses as *"no new findings"*. The incremental review's body was never fetched, never parsed, never triaged. This is brief decision 2 verbatim — *"the PR #28 finding lived in the incremental review … without the count change a body-only review reads as 'nothing new'"* (brief.md:27) — reintroduced by the bound.
**Why the spec misses it:** Decision 14's affirmative-signal block is scoped to *harvest failures* (spec.md:673-676: "the round cannot claim 'nothing new' … when a finding source did not answer"), and spec.md:1568-1569 states deliberately that a **bound** does not block an affirmative exit. A deferred review is a finding source that did not answer, but the bound was classified as "loud degradation" rather than as a source that did not answer. Round-3 F-4's fix (the `PUSH_TIME` gate) closed the over-counting arm and made this arm reachable: before it, a deferred-backlog item at least kept the signal off `verdict-landed`. 6e does print `Body harvest bounded: … deferred <ids> (re-run to pick up)`, so two report lines now contradict each other with the affirmative one on the summary line — and on the `:81`/`:381` paths even that line is lost (F-3).
**Suggested fix:** two options, either sufficient. (a) Minimal, in D5: *"A round whose bound deferred any candidate with `submitted_at > PUSH_TIME` may not report `verdict-landed` or `pre-existing-approval`; the signal degrades to `inconclusive` and 6e names the deferred incremental review."* (b) Better, in 2b step 2: *"When 2b is invoked from a 6a/6b cycle, the harvest set is the 10 oldest **pre-`PUSH_TIME`** candidates **plus every candidate with `submitted_at > PUSH_TIME`**."* This does not endanger contiguity — the deferred backlog still floors, so `HANDLED_THROUGH` and `LAST_BODY_REVIEW_ID` both stay below the gap exactly as today. Add a test row to § 29: with 11+ unhandled body-carrying reviews and a post-push body-carrying verdict review, the round must not report `verdict-landed`.

### F-2: D6's advance rule treats an unfetchable review as "failed", so the in-run mark never passes it — contradicting Decision 12's "not retried" and pinning the 10-slot harvest window for the rest of the run
**Severity:** P1
**Where:** spec § D6 advance rule (spec.md:1333-1353) vs § Decision 12 (spec.md:456-461), § D9 (spec.md:1620-1628)
**Edge case:** any harvest set whose **lowest** id is unfetchable (`404`/`410`/`451`) — the case Decision 12 added the unfetchable class for.
**What happens:** the two contiguity rules diverge, and the spec never says which reading is intended. Decision 12: an unfetchable review *"counts as handled for contiguity … and is **not retried**"*. D6: set `LAST_BODY_REVIEW_ID` to the highest id *"parsed **and** had its surviving items triaged, strictly below the round's **lowest failed**, deferred, or untriaged id"*, with the stated rationale *"It must **not** advance past a review whose fetch failed — otherwise that review is never retried by a later 6a poll of the same run."* An unfetchable review was not parsed, not triaged, and its fetch failed, so under D6's letter the mark stops below it. Consequences for the rest of the run: (i) it is re-fetched and re-404'd on **every** 6a/6b cycle — the behaviour Decision 12 forbids in the same breath; (ii) it occupies slot 1 of every subsequent 10-review harvest set, so the window never moves and no deferred review — including the incremental review — is ever reached, which is F-1's trigger with only 11 candidates instead of 21; (iii) the run's posted marker `R` *does* advance past it (Decision 12) while the in-run mark does not, so the two values disagree by design with no statement that they should. The opposite reading (unfetchable ∉ "failed") leaves D6's worked example `[100 ok, 200 fetch-failed, 300 ok] → 100` ambiguous, since "fetch-failed" is exactly the word both classes share.
**Why the spec misses it:** spec.md:1350-1353 anticipates the question and enumerates **one** difference between the two marks — *"the in-run mark … ignores whether a 6f post succeeded, the posted marker … does not"* — written before the unfetchable class existed. The unfetchable/failed split was added to Decision 12 and never propagated to D6's three-word list.
**Suggested fix:** in D6, change *"strictly below the round's lowest failed, deferred, or untriaged id"* to *"strictly below the round's lowest **retryably-failed**, deferred, or untriaged id; a review recorded unfetchable counts as handled here exactly as it does for the posted marker, so the mark passes it and it is not re-fetched"*, and extend the enumeration at spec.md:1350-1353 to name that as the second — now only — difference-free case. Add a row to § 29(ii): after a `404`, the next 6a poll of the same run must not return that review.

### F-3: every Step 2 early exit bypasses 6e, so the Decision 11 tripwires, the bound line, the unfetchable line and the size line are never reported — on the exits where a format drift is most likely to land
**Severity:** P1
**Where:** spec § Decision 11 (spec.md:393-396), § D1 `:81`/`:83` (spec.md:846-865), § D9 `:381` (spec.md:1564-1571), § D8 6e report block (spec.md:1536-1545), against `skills/review-pr/SKILL.md:81`, `:83`, `:381`
**Edge case:** CodeRabbit changes a section summary format (Decision 11's whole reason for existing) on a PR with no unhandled inline findings — a body-only review, or a re-run whose inline threads are already handled.
**What happens:** the drift detector fires into a void, and with a bounded harvest the drifted findings are then marked handled forever. A phrase drift means no section matches, so the parse yields **zero body items**. Zero body items + zero inline comments is precisely `:381`'s trigger ("Nothing to review"), and with an `APPROVED` verdict it is `:81`'s. Both are Step 2 exits: they `report … and stop` before Step 6 ever runs. Decision 11 states the tripwire's only report channel as *"the round continues with whatever parsed, and **6e** prints the tripwire line"*; D8 puts `Body parse tripwire`, `Body harvest bounded`, `Body reviews unfetchable` and `Body harvest size` in the 6e block alone. None of them is reachable from `:81`/`:83`/`:381`. The spec threaded three other things through those exits — the marker post (row 22), the scratch cleanup (D1), and the harvest-**failure** report (Decision 14, spec.md:690-693) — and not this one. Worse in combination with a bounded harvest: `R` advances, 6f posts the findings-free marker (row 22 requires exactly this at both sites), and the drifted reviews now sit **below** `PRIOR_MARK`, so no future run re-parses them. Net: CodeRabbit changed its format, the skill detected it, and the operator was told *"Nothing to review — PR is approved"*. That is the silent blindness the ticket exists to remove, arriving through the detector built to prevent it — structurally, this is the same defect Decision 11 itself records for the v1 count-only tripwire (spec.md:364-367).
**Why the spec misses it:** the tripwire's report channel was fixed at 6e in round 1, before the Step 2 exits were re-worked; each later fix to those exits (marker, cleanup, failure precondition) was written against a specific finding and none re-walked the report surface. Decision 14's clause covers "cannot confirm nothing to review" for *fetch failures* only, and a tripwire is explicitly not a failure (spec.md:395-396: "the round continues").
**Suggested fix:** name the six 6e harvest lines as one **harvest summary** block in 2b (tripwire / bounded / unfetchable / size / grouped / harvest-failure) and state in D1 and D9 that each Step 2 exit prints that block immediately before it stops, alongside the marker sentence row 22 already pins — e.g. `:81`/`:381` carry *"Before exiting, print the harvest summary and post the progress marker if 6f's post condition holds (6f)."* Extend row 22's expected text accordingly so the addition is gated, and add a § 29 row: with a drifted section summary and no inline findings, the run must print the phrase-tripwire line before its "Nothing to review" exit.

### F-4: the 64 KB–256 KB slice path and 2b step 6's unconditional body-wide phrase-scan view are mutually exclusive, and the spec does not say which yields
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec § D2 2b step 3 (spec.md:980-996) vs § D2 2b step 6 (spec.md:1039-1048)
**Edge case:** a review body between 64 KB and 256 KB — the band step 3 created specifically so the body is never read whole.
**What happens:** the implementer must silently pick one of two bad outcomes. Step 3: *"parse **by slices**: first search the file … then read only the line ranges."* Step 6: *"**First, once per review body**, compute the phrase-scan view … a **body-wide copy** in which each line has its own leading `>` markers stripped, then fenced blocks and inline-code spans masked … This runs before and regardless of the per-section work below."* Materializing a stripped-and-masked copy of a 200 KB body **is** reading the whole body into the round — the mid-round context collapse the size ceiling exists to prevent (spec.md:994-996). Skipping it instead disables the phrase tripwire for exactly the bodies most likely to have grown a new section shape. Neither branch is stated, so the failure is whichever the implementer improvises, and both are invisible in the report.
**Why the spec misses it:** the size ceiling (round-1) and the hoisting of the phrase-scan view out of the per-section loop (round-3 F-8) were written two rounds apart, in different steps, and the hoist made the view unconditional without re-checking the one path that forbids reading the body whole.
**Suggested fix:** one clause in step 6: *"On the slice path (step 3), the phrase-scan view is not materialized: run the phrase detector as a line-numbered search for the two phrases over the whole file — a search, not a trim — and mask by checking whether each hit's line falls inside a fenced block located by the same search."* That keeps the detector alive at every size and keeps the no-whole-read discipline intact.

### F-5: the compaction re-read can prove *that* a fetch failed but has no stated source for *how* it failed, though the `.err` capture survives
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec § D2 2b step 4 (spec.md:1003-1008), § D2 2b step 3 block (spec.md:952-966), § Decision 12 (spec.md:451-470)
**Edge case:** the exact condition step 4's fallback is written for — a context compaction or long poll sequence between the fetch and the classification.
**What happens:** the round-3 F-2 fix is half-durable. Step 3 deletes `body-<id>.md` on failure so *"a missing `body-<id>.md` is … the durable record of a failed fetch, independent of what the agent remembers"* ✓ — but the classification that decides floor-vs-unfetchable rests on the **printed token's error text** (spec.md:471-474), which is conversational state and is lost by the same compaction. Step 4 then instructs *"Classify it per Decision 12 (retryable → floor; `404`/`410`/`451` → unfetchable)"* with no input to classify from. Decision 12's default ("any status or error text not listed here" is retryable) saves it from being unsafe — the review floors and the run ends `inconclusive` — but the spec does not say that is the intended landing, so an implementer may equally improvise "unfetchable" (permanent finding loss) or guess from the review's absence. The same gap bites 2b step 3's end-of-pass session-condition test, which needs *every* review's status after the pass. And the answer is already on disk: the block redirects stderr to `body-<REVIEW_ID>.md.err`, which the `rm -f` deliberately does **not** delete, so `gh: Not Found (HTTP 404)` is sitting there.
**Why the spec misses it:** the fix targeted the *stdout* capture (the thing that could be mis-parsed) and did not notice that the *stderr* capture is the surviving half and the one the classification actually needs.
**Suggested fix:** in step 4, after the missing-capture sentence: *"Read `body-<id>.md.err` for the status text and classify from it; if that file is missing or empty, the status is unknown and Decision 12's retryable default applies — floor, never write off."* Same clause in step 3 for the end-of-pass session-condition test.

### F-7: D1's "every exit path" enumeration is not every exit path, so leftover scratch directories accumulate and make the ">1 candidate → refuse" recovery rule fire on healthy runs
**Severity:** P3
**Where:** spec § D1 (spec.md:760-769, :771-782), against `skills/review-pr/SKILL.md:122`, `:385`, `:387`
**Edge case:** a run that stops on an exit D1 does not name — `:385` "Branch protection blocks push: report the error, don't retry", `:387` "CodeRabbit timeout/down … report and stop", or Step 4's unresolvable test failure — followed by a later run on the same PR that loses `<SCRATCH>` to a compaction.
**What happens:** the recovery rule degrades from "safe" to "unusable". D1 claims *"The directory is removed on **every** exit path"* and then enumerates five: 6e, `:79`, `:81`, `:83`, `:381`. The three exits above are outside that list, and an interrupted agent session leaves nothing behind at all — so `"${TMPDIR:-/tmp}"/review-pr-<N>-*` accumulates one orphan per aborted run on that PR. The recovery rule (correctly, per round-3 F-6) refuses to guess when the glob returns more than one candidate, so the *first* orphan permanently converts every future compaction on that PR into `HARVEST_FAILURE` → `inconclusive`, with a message that points at GitHub rather than at `/tmp`. Loud rather than corrupting, which is why this is P3, but it is a self-inflicted trip-hazard on a machine that reviews the same PR repeatedly.
**Why the spec misses it:** the cleanup enumeration was derived from the *Step 2* exits named in the round-2 finding; the Step 4/5/6 edge-case exits at `:385`/`:387` were never in view, and the recovery rule was written two rounds later against a clean `/tmp`.
**Suggested fix:** either extend D1's enumeration to "any exit, including the push-failure and CodeRabbit-down stops at `:385`/`:387`", or make the recovery rule tolerant of orphans instead of exits tolerant of orphans: *"ignore candidates older than this run's start; if exactly one remains, adopt it; if more than one remains, refuse."* The second is more robust, since an interrupted session leaves no exit path to hook.

### F-8: the idempotency guard suppresses a re-run's dispositions when the harvest identity repeats but the triage outcome differs
**Severity:** P3
**Where:** spec § Decision 12 Guard (spec.md:546-560), § D7 (spec.md:1432-1444), § D8 6e (spec.md:1536-1537)
**Edge case:** a re-run over a harvest set that reproduces exactly (same reviews, same retryable failure floor, therefore same `r<R>:h<IDS>`) but whose triage lands differently — the code moved between runs, so an item that was `fix` is now `already-fixed`, or an item skipped in run 1 was fixed in run 2 under a new SHA.
**What happens:** the second run's disposition list is silently not posted. The guard's key is `(R, harvest ids)` — deliberately not content-derived (the sha1sum/injection rejection at spec.md:415-425) — so it means "this harvest was dispositioned", not "these dispositions were recorded". The PR then carries run 1's judgments for findings run 2 disposed of differently, which is the audit-trail hole the brief names, narrowed to a repeat harvest. 6e does say `dispositions not posted — guard-skipped`, so an operator who reads the report can reconstruct it — that observability is why this is P3 and not higher.
**Why the spec misses it:** the guard was designed against the duplicate-comment failure and validated on the case where the outcome is identical ("either the retry fails again and the round has nothing new to say, or it succeeds…", spec.md:428-433). The third case — same key, different disposition — is not in that enumeration.
**Suggested fix:** either state the tradeoff explicitly in Decision 12 (*"a re-run whose harvest identity repeats but whose triage lands differently does not re-post; 6e's guard-skipped line is the record, and the operator can compare"*), or add the round's `HEAD_SHORT_SHA` to the marker as a third field so a fixed-since-last-run outcome posts. The first is a one-sentence clarification and preserves the injection-free literal-only rule.
