### F-1: The two shipped strings that describe an unfetchable review say it is "excluded from the resume mark" — the exact opposite of Decision 12, D9 and test row 29(ii)
**Severity:** P0
**Where:** spec.md:1383 (§ D7, the 6f body `text` block) and spec.md:1451 (§ D8, the 6e report `text` block) vs spec.md:446-448 (§ Decision 12), spec.md:1540-1543 (§ D9), spec.md:1763-1764 (row 29(ii))
**Claim:** the 6f body template, spec.md:1383: `` - Review <id> unfetchable (<code>) — excluded from the resume mark; not retried ``. The 6e report template, spec.md:1451: `` - Body reviews unfetchable: none / <id> (<code>) — not retried, excluded from the resume mark ``.
**Why this is wrong:** Decision 12 says the opposite, and says it as the load-bearing property — spec.md:446-448: *"the review is recorded as **unfetchable**, **counts as handled for contiguity**, is named in this round's 6f comment and in 6e, and is not retried."* D9's new bullet spec.md:1540-1543: *"A round's only progress is an unfetchable review — no floor, no findings, but **`R` advances**; 6f's third post condition posts the findings-free form naming it, **so the marker moves past the dead review** and no later run re-fetches it."* Test row 29(ii) spec.md:1763-1764 pins the same behaviour: *"must post the findings-free 6f comment naming it, **so the marker advances past that id**."* An unfetchable id is therefore included in `HANDLED_THROUGH` and can *be* the value of `R`; "excluded from the resume mark" states that it is not. These two strings are not spec commentary — they are the verbatim templates the implementer copies into `skills/review-pr/SKILL.md` (the Design preamble, spec.md:679-681, names "the fenced `bash` / `text` blocks verbatim, comments included" as shipped text). An implementer who follows the shipped text over the surrounding Decision prose implements the pre-fix behaviour: the dead review is excluded from the mark, `PRIOR_MARK` never moves past it, and every later run re-fetches, re-404s and re-reports it — precisely the P0 that edge-cases round 2 F-1 closed, reintroduced through the shipped surface. Per this review's own rule, a block that disagrees with the prose around it is P0 because implementers follow blocks.
**Suggested fix:** at spec.md:1383 write `` - Review <id> unfetchable (<code>) — counted as handled; not retried ``, and at spec.md:1451 write `` - Body reviews unfetchable: none / <id> (<code>) — not retried, counted as handled so the resume mark passes them ``. Nothing else in either block changes.

### F-2: Decision 14 still classifies `403` as non-retryable, contradicting Decision 12, D9 and test row 29(iii)
**Severity:** P1
**Where:** spec.md:646-649 (§ Decision 14) vs spec.md:439-448 (§ Decision 12), spec.md:1536-1539 (§ D9), spec.md:1765-1767 (row 29(iii))
**Claim:** spec.md:647: *"A review recorded as **unfetchable** (Decision 12: a non-retryable `403`/`404`/`410`/`451`) is reported but is *not* a standing failure…"*
**Why this is wrong:** Decision 12 spec.md:439-446 now says the opposite, explicitly and with the reason: *"**Retryable** … is the **default**: `5xx`, **`403`** (GitHub uses it for primary and secondary rate limits and for SSO/scope problems — session conditions that clear on re-run …) … Only three statuses are **non-retryable** … `404`, `410`, `451`."* D9 spec.md:1536-1539: *"A `403` is **not** in this class … it floors and is retried."* Test row 29(iii) spec.md:1765-1767 requires that a `403` **floor**, end `inconclusive`, and leave the marker below that id. Decision 14's parenthetical is the one surviving copy of the pre-fix taxonomy, and it is in a *Decisions* section — the part an implementer treats as normative when writing the harvest-failure rules. Following it, a rate-limited or SSO-blocked session marks every affected review unfetchable → excluded from the floor → counted as handled → `R` advances past them → they sit below `PRIOR_MARK` forever and are never harvested again. That is permanent finding loss, i.e. the defect this ticket exists to remove, and it violates Decision 12's own stated invariant (spec.md:479-481: *"no review id at or below a posted marker … failed a fetch"*). It is also a direct contradiction of a P1 the closure manifest claims fixed. Verified that `rc` alone cannot separate the cases: a 404 and a 403 both return `rc=1` (403 measured in round 2; 404 measured live this round), so the classification rests entirely on the printed error text and therefore entirely on which list the implementer copies.
**Suggested fix:** at spec.md:647 change *"(Decision 12: a non-retryable `403`/`404`/`410`/`451`)"* to *"(Decision 12: a non-retryable `404`/`410`/`451` — `403` is retryable and floors)"*.

### F-3: 2b step 2 sources the candidate set from "Step 2 fetch (b)" in rounds 2+ as well, which is a stale snapshot and defeats Decision 2
**Severity:** P1
**Where:** spec.md:878-880 (§ D2, 2b step 2) vs spec.md:1180-1184 and spec.md:1201-1203 (§ D5), spec.md:53-61 (§ Decision 2)

**Why this is wrong:** the parenthetical extends the sentence to rounds 2+ but changes only the *threshold*, leaving the *source* pinned to Step 2's one-time fetch. Step 2's fetch (b) is issued once, before any push; the reviews rounds 2+ exist to harvest — CodeRabbit's incremental review bodies — do not exist yet when it runs. Under this sentence a round-2 candidate set drawn from fetch (b) and filtered `id > LAST_BODY_REVIEW_ID` is **empty by construction**, and the incremental review's body findings are never harvested. That is exactly the failure Decision 2 records as load-bearing from the brief (spec.md:66-67: *"the PR #28 finding lived in the *incremental* review; a fix confined to Step 2 would not have caught it"*), and it is the brief's decision 2 verbatim (brief.md:27). So two sections that both ship name two different inputs for the same set, and the one inside the procedure the implementer will write as `### 2b.` names the wrong one. This text is new this round (the round-2 wording was *"The set is every review … with `id > PRIOR_DISPOSITIONED_REVIEW_ID`"*, with no source clause), so it is a new variant introduced by the candidate/harvest split rather than a carried-over defect.
**Suggested fix:** at spec.md:878-879 make the source per-invocation: *"The **candidate set** is every body-carrying review the invoking step's review list returned — Step 2 fetch (b) when 2b runs from Step 2, 6a's body-carrying poll when it runs from 6a/6b — with `id > PRIOR_DISPOSITIONED_REVIEW_ID` (rounds 2+: `id > LAST_BODY_REVIEW_ID`), ordered ascending."*

### F-5: `HANDLED_THROUGH` is defined in terms of "a posted comment", which is circular for the round computing its own marker
**Severity:** P2
**Pre-ship recommended:** yes
**Where:** spec.md:465-468 (§ Decision 12) vs spec.md:490-500 (§ Decision 12's worked example) and spec.md:437 (the failed-post floor cause)
**Claim:** spec.md:465-468: *"`HANDLED_THROUGH` — the highest id such that **every** body-carrying review in `(PRIOR_MARK, that id]` was fetched, parsed, and had all its surviving items dispositioned **in a posted comment**."*
**Why this is wrong:** `R` is computed *before* the round's 6f post (D7 spec.md:1345: *"`<R>` is computed by Decision 12's run-scoped contiguity rule"*, and the guard block that consumes `r<R>` runs before `gh pr comment`). At that moment the current round's items are dispositioned only in the comment about to be written, not in a posted one. Read literally, no review a round handled itself can ever enter `HANDLED_THROUGH`, so on a first run `HANDLED_THROUGH` is `0`, `R` is the sentinel `0` forever, and the marker never advances — the "recomputes the identical harvest set forever" defect Decision 12's own "Progress does not depend on findings" rule (spec.md:507-519) exists to prevent. The intended semantics are unambiguous from two other places: the worked example at spec.md:496-500 has round 1 post `r200` for reviews it dispositioned *in that very comment*, and spec.md:437 makes "a round whose 6f post failed" a *floor cause*, i.e. the post is assumed to succeed and is retro-floored if it does not. A careful reader unravels it; the definition as written does not say it.
**Suggested fix:** at spec.md:467-468 change *"dispositioned in a posted comment"* to *"dispositioned in a comment that has posted, or in the comment this round is about to post — a post that then fails becomes a floor cause (below), which retracts the claim."*
